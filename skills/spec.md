下面这个 Prompt 的重点不是让 Code Agent 把文档改写成 YAML，而是让它把已有设计文档转化为可执行、可验证、可追溯的 Spec，并识别哪些要求目前还无法被可靠判定。

# 任务：将设计文档转化为可执行、可验证的 Spec

请阅读当前代码仓库中的设计文档，将其转化为能够指导 Coding Agent 实现、由自动化验证器独立验收的 Spec。

不要简单地将文档改写成结构化格式。你的目标是建立从需求意图、行为契约、正确性判据到验证证据的完整链路。

## 工作要求

1. **理解并拆解需求。** 提取业务目标、行为要求、输入输出、状态转换、不变量、权限边界、异常处理、非功能约束及明确的非目标。保留原始文档来源和追溯关系。
2. **识别不确定性。** 区分明确要求、合理推导、未经确认的假设和相互冲突的要求。不得自行编造业务规则。遇到影响正确性或安全性的关键歧义时，列出问题并暂停相关 Spec 的最终定稿；其他部分可以继续。
3. **定义可判定契约。** 为每项要求明确前置条件、行为、后置条件、边界情况、失败行为及验收标准。对于无法完全自动判定的要求，明确其限制、所需人工判断及补充证据。
4. **建立独立 Oracle。** 明确每项验收判据的来源及可信度，区分权威业务规则、专家确认案例、形式化约束、统计评估和人工评审。不得仅因为实现和测试均由 Agent 生成且测试通过，就认定实现正确。关键判据必须有独立依据；依据不足时标记为待确认。
5. **建立可执行验证。** 检查仓库现有技术栈、测试框架和 CI 配置，优先复用已有工具。为 Spec 建立适当的机器可读结构、Schema 校验、测试用例、断言或其他验证器。验证器必须有明确的执行入口和通过条件，不能只写自然语言测试计划。
6. **验证 Spec 本身。** 检查要求是否存在歧义、冲突、不可判定条件、遗漏的边界、缺少 Oracle、不可执行的验证项或无法追溯的要求。重点覆盖异常路径、权限边界、未知状态、失败恢复、并发和不变量。
7. **防止自证与标准漂移。** 实现、测试和验收判据应有明确的职责边界。未经授权，不得为了让测试通过而删除要求、降低阈值、修改预期结果或缩小覆盖范围。Spec 或 Oracle 的变更必须记录差异、原因和批准要求。
8. **生成可复核证据。** 验证结果必须关联 Spec 版本、代码版本、测试版本、输入数据、执行环境和实际结果。严格区分 `PASS`、`FAIL` 和 `INCONCLUSIVE`；缺少必要证据、验证未执行或判据不可信时，不得报告为 PASS。

## 执行方式

按以下顺序工作：

**阶段 A：仓库与文档勘察**

- 找出相关设计文档、现有实现、数据模型、接口、测试和 CI 配置。
- 建立需求到现有实现的初步映射。
- 不要在理解现状之前大规模创建新文件或重构代码。

**阶段 B：Spec 建模**

- 将需求拆分为粒度适当、可独立追溯的 Spec 条款。
- 为每项条款分配稳定 ID。
- 区分业务契约、技术契约、质量属性及组织治理约束。
- 标明每项要求的风险等级、Oracle 来源、验证方式和成熟度。
- 对有歧义的条款明确标记，不得伪造确定性。

**阶段 C：验证器与基准建立**

- 优先使用独立的权威规则、人工确认的基准案例和确定性断言。
- 对适合属性测试的要求，定义输入空间、性质和边界。
- 对难以获得精确预期结果的要求，考虑差分测试、蜕变测试、历史缺陷回放或人工盲评。
- 为关键要求建立能够检出代表性错误的测试。
- 不要把 LLM Judge 当作所有类型问题的通用 Oracle。

**阶段 D：执行与缺口分析**

- 先验证 Spec 和验证器，再运行现有实现的测试。
- 如果任务明确要求实现，且需求与验收判据已足够明确，再按 Spec 修改代码；否则先完成 Spec 和验证基础设施，列出阻塞问题。
- 执行相关测试，记录真实结果、失败原因和未验证项。
- 在条件允许时注入代表性错误，检验验证器能否检出错误。
- 不得将未执行的验证描述为已通过。

**阶段 E：交付**\
在仓库中生成并提交适当的文件，至少包含：

- Spec 文件：机器可读的契约。
- Spec Schema 或等效校验机制：验证 Spec 结构与必要字段。
- 验证器及测试用例：真正执行契约检查。
- 基准数据及来源说明：支撑关键 Oracle。
- 追溯映射：原始文档条款 → Spec ID → 验证器/测试 → 证据。
- 验证报告：通过、失败、证据不足、未覆盖和未解决的问题。
- 使用说明：如何校验 Spec、运行验证及查看结果。

文件格式、目录结构和工具选型应基于仓库现状决定，不要为了追求统一格式而引入不必要的框架。

## 完成标准

只有满足以下条件，才可以声称本任务完成：

- 原始文档中的关键要求均有追溯关系，遗漏项有明确说明。
- 关键要求具有明确、可判定的验收条件。
- 关键 Oracle 有可信来源，不能依赖被测实现自我证明。
- Spec 可通过机器校验，关键验证项可实际执行。
- 关键异常路径和代表性错误有对应测试。
- 测试结果与证据可复核、可复现。
- 未解决的歧义、未验证要求和已知限制被明确披露。
- 没有通过降低验收标准来制造成功。

请先检查仓库并形成判断，再执行任务。优先交付一个经过验证的最小闭环，而不是一次性建立庞大、空洞的 Spec 体系。

最终报告请简洁说明：生成了什么、覆盖了什么、实际验证了什么、哪些结论仍不可信，以及下一步最值得解决的问题。

### 使用时的一个关键建议

把原始设计文档放在 Code Agent 能访问的仓库中，或者明确指定文件路径。不要只把文档转换成 Spec，还要要求它建立“文档条款 → Spec → 验证器 → 执行证据”的追溯关系。

否则，Code Agent 很容易产出格式漂亮的 YAML，却没有真正可执行的验证能力。

另外，这个 Prompt 默认先完成 Spec 和验证基础设施，再决定是否修改业务代码。如果你希望它直接把现有系统也改造到符合 Spec，可以在末尾加一句：

> 在 Spec、关键 Oracle 和验收标准明确后，继续检查现有实现与 Spec 的差距，并直接完成必要的代码修改、测试和验证。遇到关键业务歧义时，不得自行猜测或放宽标准；先完成不受该歧义影响的工作，并将阻塞项单独列出。
