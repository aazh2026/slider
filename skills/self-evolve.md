下面这个 Prompt 的重点不是让 Code Agent 「再检查一遍」，而是让它**用同一条纪律持续加固这个仓库自己的验证链路**。

# 任务：自我进化循环 —— 找出「断言抓不到、但人眼看得出来」的那一层，并把它补上

AI PPT Studio 的 Spec / 验证器 / 追溯矩阵已经建好（`spec/`，详见 `skills/spec.md` 那轮任务的产出）。
现在缺的不是「更多文档」，而是**验证链路本身会漏掉什么**。

## 为什么要做这件事

已经用眼睛抓到一个断言抓不到的真缺陷（2026-11-04）：

> 工作台主画布被 `flex-shrink` 压成 480×1080 的**竖条**，幻灯片被缩成中间一条，上下大片空白。
> 而 IR 里的 `canvas` 仍然是 `{1920, 1080}` —— **96 条 E2E 断言全绿**。
> 单元测试更是不可能抓到：那不是逻辑错，是「渲染出来的东西不对」。

这类缺陷的共同点是：**IR 对、状态对、断言全过，只是「屏幕上看到的东西」不对。**
只看断言不看画面，就永远发现不了。

## 每轮循环要做的事

**只挑一件事做完**。不要一轮里铺开做五件 —— 那样每件都做一半，证据链就断了。

优先级从高到低：

1. **看画面。** 跑可见 E2E，用眼睛逐张看 `spec/evidence/e2e-media/<链>/shot-*.png`，
   拿录像回放关键交互。凡是「看着不对但断言全绿」的地方，就是本轮的猎物。
   典型信号：比例不对、留出大片空白、元素被裁掉、层叠错位、
   控件在但点不动、文案与状态不一致、缩略图与主视图长得不一样。
2. **补判据。** 找到缺陷 → 修实现 → 在 `spec/spec.yaml` 里把「这条到底要求什么」写成**可机械判定**的判据。
   判据必须断言**可观测的量**（元素盒比例、像素位置、接口返回值、数据库里的行），
   而不是断言「DOM 里存在某个字符串」—— 后者正是这次漏掉缺陷的那种弱断言。
3. **补元验证。** 给新判据配一条注入错误：把实现改坏，验证器必须报错。
   注入的必须是**代表性错误**（同一类错误里最典型的那种），不是不完整的错误。
   跑 `bun run spec/verify/mutation-check.ts` 确认 `caught: true`。
4. **补既有判据的元验证缺口。** 追溯矩阵 §三「哪些结论仍不可信」里列的
   「没做注入错误检查」的判据，一条一条补上。
5. **补判据的盲区。** 追溯矩阵 §1.3 未覆盖清单、§2.5 INCONCLUSIVE 清单里，
   凡是**不依赖外部条件**（不需要真实密钥、不需要业务方拍板）的，逐条推进。
   需要外部条件的（真实模型 P95、质量闸门分数线）**跳过并原样保留**——
   不许用降级模式、模拟值或自造阈值把它们「变成通过」。

## 不可让步的四条

1. **不编造业务规则。** 文档没写的不要替它决定。合理推导要显式标注推导依据；
   未确认的假设进歧义清单；关键歧义**暂停相关条款定稿**，其余照常推进。
2. **不自我证明。** 「实现和测试都是 Agent 写的，测试过了」不是正确性证据。
   关键判据的 Oracle 必须来自被测系统之外；`self-derived` 不能单独支撑高风险条款。
3. **不可判定就承认。** 三态结论 `PASS` / `FAIL` / `INCONCLUSIVE`。
   **缺必要证据、验证未执行、判据不可信，一律 INCONCLUSIVE**，不许报 PASS。
   没跑过的验证不是通过。
4. **不用降低标准换成功。** 删要求、降阈值、改预期、缩覆盖来让测试变绿 —— 这是最严重的失败模式。
   确需调整，必须记录：改了什么、为什么、谁批准。新阈值不得低于同类型条款的既有下限。

## 每轮的交付格式

一轮结束时，用四段说清楚（不要罗列全部待办）：

1. **这一轮找到了什么** —— 缺陷的现象、根因、可复现的证据
2. **改了什么** —— 实现、判据、注入用例，分别一行
3. **验证到了什么** —— 真跑了什么、结果、证据落在哪个文件
4. **这一轮没解决什么** —— 以及**下一轮最值得做的一件事**（只挑一件）

## 操作须知（踩过的坑，别再踩一遍）

- **一条链一个 `bun test` 进程**。多条链塞进一个进程，第 5～6 条链开始页面起不来，
  浏览器死掉后 `bun test` 永远不退出，整轮流水线被一条链拖死。编排器在 `spec/verify/run-e2e.ts`。
- **跑批只许杀自己进程树里的浏览器**。浏览器是本链 `bun test` 进程的子进程，
  顺着 ppid 认领；用全局 pid 差集去清理会**杀掉别人的浏览器**，
  症状伪装成「页面炸了」。缺陷回放见 `spec/verify/chain-isolation.test.ts`。
- **只跑部分链时，证据不许写进 `spec/evidence/junit-e2e.xml`**。
  那是追溯矩阵**唯一**的 E2E 证据来源，被冲掉的话下一轮所有 E2E 判据都会变成 INCONCLUSIVE，
  而报告看起来只是「很保守」。子集跑写 `junit-e2e-partial-<链>.xml`。
- **Playwright 的 `getByTestId` 是全等匹配**，不是子串匹配 —— 前端一改名，
  它不会「匹配到别的元素」，只会**永远等不到**，每个用例卡满 15 秒超时。
  `spec/verify/testid-contract.test.ts` 有静态对账守卫，改前端 testid 时留意它。
- **注入检查跑完源文件必须还原**。每条注入走「基线 PASS → 注入必须 FAIL → 还原后重新 PASS」三步，
  第三步就是还原校验；跑完 `git diff` 看一眼，别把注入留在源码里。
- **跑一次全链路**：`bun run spec`（结构 → 类型 → 判据 → E2E → 注入 → 追溯矩阵）。
  想先看画面：`bun run spec/verify/e2e-only.ts --visible --video --shots`。
- **子集跑不影响全量证据**；正式出报告的证据必须来自全链路。

## 结束条件

这一轮**不是**要「把所有事做完」。每轮只交付一个闭环：

```
发现缺陷（看得见） → 修实现 → 写成可判定的判据 → 注入证明判据抓得住 → 全链路绿 → 证据落盘
```

闭环完整地转一圈，比铺开做十件事然后每件都没证据强得多。
