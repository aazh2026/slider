# AI PPT Studio · 可执行规格（Spec）

本目录把 `docs/` 下的五份设计文档拆成了**结构化、可执行、可验证、可追溯**的契约层。

```
需求意图 → 行为契约 → 正确性判据 → 独立 Oracle → 可执行验证 → 执行证据
```

任何一环断了，Spec 就退化成「看起来很完整的文档」。本目录的每个文件都服务于这条链路上的一环。

---

## 快速开始

```bash
bun run spec/verify/all.ts      # 跑完整条链路（推荐）
```

**退出码就是结论**（判定逻辑在 `verify/pipelineVerdict.ts`）：

| 退出码 | 含义 |
|---|---|
| `0` | 全链路通过 —— 每一层都跑出了结论，结论都是「通过」 |
| `1` | 有结论，结论是「不通过」—— **判据不满足，不该放行** |
| `2` | 有环节**没跑出结论** —— 工具链/环境坏了，这一层的结论一律不算数 |

`1` 和 `2` 的分界是这一轮之前被混成 `0` 的那件事：
**「跑红了」是有结论的**（结论是坏的，可以照着修），
**「压根没跑」是没有结论的**（旧的证据不能拿来当这一版的证明）。
而 `docs/testing-strategy.md` §7.1 写的是「Stage 2 任何失败 → 阻断、
Stage 3 E2E 失败 → 阻断」—— 流水线的出口必须对得上这句话。

等价的分步命令：

| 命令 | 作用 |
|---|---|
| `bun run spec:schema` | 校验 `spec/spec.yaml` 是否符合 `spec/spec.schema.json` |
| `bun run spec:test` | 执行全部验收判据（`bun test spec/verify/`） |
| `bun run spec:mutation` | 注入错误检查 —— 验证器抓不抓得住错 |
| `bun run spec:traceability` | 从 `spec.yaml` + 执行产物重新生成 `spec/traceability.md` |

调试注入检查时可以只跑指定的判据（**正式出报告必须跑全量**）：

```bash
MUTATION_CHECK_DRY_RUN=1 bun run spec/verify/mutation-check.ts          # 只校验锚点，不注入
MUTATION_CHECK_ONLY=AC-E2E-011 bun run spec/verify/mutation-check.ts   # 只跑一条
```

**依赖**：Bun ≥ 1.3.11（`bun test` 内置）、Python 3 + `jsonschema`（仅用于结构校验）、Node 侧的 `typescript`（类型检查）。
`jszip` 与 `bun-types` 是 devDependency —— 前者用于**回读** PPTX 产物（pptxgenjs 自己写包用的就是它），后者只为类型检查。

## 看见浏览器在干什么

默认的 E2E 是**无头**的 —— 流水线里没有显示器，无头是唯一能跑的选择。
但"无头跑过了"和"人眼看过它跑过"是两件事：
前者只证明断言成立，后者才排除「页面其实白屏、断言恰好没查那里」这类假绿。

所以 E2E 入口带一组**只影响跑法、不影响任何断言**的可视化开关：

```bash
bun run spec/verify/e2e-only.ts --visible --video --shots --slowmo=120 --hold=500
# 或
bun run test:e2e:visible
```

| 开关 | 效果 |
|---|---|
| `--visible` | 弹**真窗口**（`E2E_HEADFUL=1`）—— 人眼直接看浏览器被驱动 |
| `--video` | 每个会话录一段 `.webm`（`E2E_VIDEO=1`）—— 事后逐帧回看 |
| `--shots` | 每个会话结束时留一张整页截图（`E2E_SHOTS=1`） |
| `--trace` | Playwright trace（`E2E_TRACE=1`）—— `bunx playwright show-trace` 可交互回放 |
| `--slowmo=N` | 每个动作之间放慢 N 毫秒（`E2E_SLOWMO=N`）—— 看清动作序列 |
| `--hold=N` | 每个会话的页面在屏幕上多留 N 毫秒（`E2E_HOLD_MS=N`） |

产物落在 `spec/evidence/e2e-media/<链>/`，按链分子目录、文件名可读
（`video-01.webm` / `shot-01.png` / `trace-01.zip`）。

两条实现上的坑，踩过才知道：

- **有头模式下浏览器的可执行文件不叫 `Chromium`** —— macOS 上是
  `ms-playwright/chromium-1248/chrome-mac-arm64/Google Chrome for Testing.app/…`。
  清理残留进程时按 `Chromium` 匹配会**一个都匹配不到**，
  于是有头模式跑完窗口全留着没人管。现在统一按**安装目录**
  `ms-playwright/chromium` 匹配，无头（`chromium_headless_shell`）与有头都命中，
  而用户自己开的 Chrome 不命中。
- **截图要在上下文关闭之前拍，录像要在关闭之后取** —— 页面一关
  `page.screenshot()` 直接抛 "Target page, context or browser has been closed"；
  录像则是 Playwright 随上下文关闭才写完的，关闭之前 `saveAs` 拿到的是半截文件。

## 怎么读 `spec.yaml`

一条 clause = **一个可以独立写出一条验收判据的原子要求**。

```yaml
- id: SPEC-CORE-003              # 编号发布后不再重排
  title: 元素 ID 在整个项目内全局唯一
  type: technical                # business | technical | quality | governance
  risk: high                     # high | medium | low
  statement: "同一项目内所有元素的 id 必须两两不同"
  source:                        # 必填 —— 必须能定位回原文
    doc: "docs/architecture.md"
    section: "§12 ADR-012"
    quote: "……"
  acceptance:                    # 每条判据必须可机械执行
    - id: AC-CORE-003
      criterion: "……"
      oracle:                    # 必填 —— 「正确答案」从哪来
        tier: formal             # authoritative | expert | formal | statistical | human | self-derived
        source: "……"
        confidence: high
      verification:
        kind: test
        target: "spec/verify/core-layout.test.ts::element-ids-unique-across-slides"
        command: "bun test spec/verify/core-layout.test.ts"
        pass_when: "退出码 0，且该用例未被 skip"
      maturity: automated        # automated | semi | manual | none
  maturity: automated
```

### Oracle tier 怎么看

| tier | 含义 | 能不能单独支撑一条 high 风险条款的 PASS |
|---|---|---|
| `authoritative` | 权威业务规则原文（需求文档明确条款） | 能 |
| `expert` | 专家 / 领域负责人确认的基准案例 | 能 |
| `formal` | 类型、schema、不变量等形式化约束 | 能 |
| `statistical` | 统计评估、分布性判据 | 需辅以其他 tier |
| `human` | 人工评审 / 盲评（须记录评审者与量表） | 需辅以其他 tier |
| `self-derived` | **从被测实现反推出来的** | **不能** |

`self-derived` 不是不能写，但必须显式标注 —— 它只能防回归，不能证明实现正确。

### 成熟度不等于结论

- `maturity: automated` —— 判据**有**可执行验证器
- `maturity: planned` —— 判据写好了，验证器**还没建**（≠「已通过」）
- `maturity: none` —— 判据根本写不出来（如阈值未给出）

**真实结论看 `spec/traceability.md`**，三态：`PASS` / `FAIL` / `INCONCLUSIVE`。没跑过的验证一律 `INCONCLUSIVE`。

## 改 Spec 的流程

1. 改 `spec/spec.yaml`（条款、判据、oracle、成熟度）
2. `bun run spec:schema` —— 结构合法性
3. `bun test spec/verify/` —— 新判据是否真的被执行、是否真的能抓到错
4. `bun run spec:mutation` —— 为新的关键判据补一个注入用例
5. `bun run spec:traceability` —— 重新生成矩阵

第 4 步不能省。**「测试通过」本身不证明测试有效** —— 只有「把实现改坏，验证器报错」才能证明。

## 验证器怎么写

三条规矩：

1. **断言写在 test 文件里，不写在 helper 里。** helper 只造夹具、抽文本。判定逻辑藏进 helper 会导致失败时说不清是哪条判据挂了。
2. **验产物，不信返回值。** PPTX 导出要解包回读 XML；SVG 要读真实字符串；不要断言「导出函数返回了一个我们传进去的东西」。
3. **用外部可辨识标记，不要用「不等于空」这种弱断言。** `helpers.ts` 里的 `MARKER = 'ZQ7MARKER'` 就是干这个的 —— 任何硬编码演示文案都不可能命中它。

## 已知的状态

**具体数字请看 `spec/traceability.md`**（由 `spec/verify/traceability.ts` 从执行产物现场生成，不手写）。
本节只写**不会随代码变动的实质事实**：

- 后端（`apps/api`：Hono + Drizzle + PGlite + ModelRouter + 鉴权 + 导出）**已实现**，
  领域内核抽在 `packages/core`（`@ppt/core`），前端已接到真实后端上。
- **目前没有 FAIL 判据**。追溯矩阵 §2.2 为空即为证据。
- **1 条判据被修订过 —— `AC-EXP-001`，记录在 `spec.yaml` DEC-003。**
  原写法「每个 IR 字符串完整出现在某一个 `<a:t>` 运行里」对**含换行**的 IR 字符串永远不可满足
  （PPTX 段落以换行为界，pptxgenjs 见到 `\n` 必定拆段，DrawingML 的 `<a:t>` 里也不存在字面换行）。
  判据改为以「行」为单位，并追加**集合相等**这一更强的不变式（既不缺正文、也不多出固定文案、
  任何两行不得拼在同一运行里）。判据的权威来源（EXP-15 / EXP-17「回读产物校验关键文本存在」）未动。
  **这不是降标准换绿 —— 唯一被放宽的是那个格式上不可能的『一个字符串一个运行』，
  同时被收紧的是反串行能力。**
- **1 条判据验错了实现路径 —— `AC-EXP-003`，记录在 `spec.yaml` DEC-015。**
  判据写的是「PNG 光栅化必须是 3840×2160（= slide.canvas 的两倍）」，
  权威来源是 `docs/backend-features.md §J EXP-02`：「`@resvg/resvg-js` 3840×2160，**无需浏览器**」。
  原文指的从来是**服务端 resvg** 那条路，可判据验的是 `ExportEngine.exportSlideAsPng` ——
  核心库里那条**浏览器 canvas** 路径，全仓库除验证器外**没有任何调用者**

- **注入检查自己造成的假过期，已经修掉**（2026-11-05）。

- **新鲜度判定自己造成的假过期修完之后，剩下的是「假 fresh」**（2026-11-05）。

  比多报危险得多（多报只是保守，漏报是撒谎）。

    基线一被动过，那条结论当场变「已过期」，并点名是哪个文件。
  · **兜底也看得见数据文件**：§2.1.1 的兜底清单原来只扫 `.ts/.tsx`，
    现在也扫数据文件 —— 就算**谁都没声明**，被动过的数据文件至少会被点名，
    而不是无声无息。
  复现与验证见 `spec/verify/verdictFreshness.test.ts` 的「数据依赖」两节
  （含一条反面用例：拿掉声明，同一个基线被动过，判定又看不见它了）。
- **「假 fresh」的另一半：注入侧也看不见数据依赖**（2026-11-05，第 11 轮）。
  上一条修的是**主证据侧**（§2.1.1）。注入侧（§2.4.1）比的是报告里记的
  **文件指纹** —— 而报告只记了「验证器」与「被改的源文件」两份**代码**，

    判定时一并比：变了就是 **stale**；**报告没记**（旧格式）就说清不了 ——
    **unknown ≠ fresh**。
  · 验证器**已经不声明**某个数据依赖时，**不算过期** ——

- **画布放大后，左边那一块曾经永远滚不到（2026-11-05）** ——
  还是用眼睛看出来的：可见跑批的 `presentation/shot-04.png` 里，

  放大到超过适配档位后画布比可视区宽，**center 把溢出量平均分到两侧**，

  ①对齐改成 `safe center`（放得下就居中，放不下就贴左/贴上，溢出全甩到可滚的一侧）；
  ②适配缩放改用 `ResizeObserver` 跟踪容器尺寸 —— 原来只监听 `window.resize`，
  容器因面板收起/展开而变宽时缩放档位会**停在旧值上**，画布就比可视区宽。
  判据 `AC-CORE-012`（放大后两侧都滚得到）与 `AC-CORE-013`（容器变了自动重新适配）守着，
  注入检查里配了三条注入（`safe center` 改回 `center` × 水平/垂直、不再观察容器变化）。

  真凶不是验证器，是**环境被抢**：注入检查的本质是
  「改坏源码 → 跑验证器 → 还原源码」，
  两个跑批同时跑时，对方会把我们的注入还原掉（浏览器里跑的是干净源码 → 验证器当然通过），
  或者把它的注入留在树上（我们的覆盖率门禁跑出一个**假的失败**：
  软删除的项目居然还能打开，期望 404 拿到 200）。
  这类结论一旦落进报告，下一步就会去"修"一个**没毛病的验证器**。
  修法两处：
  ①`spec/verify/mutationLock.ts` —— 跑批互斥锁（锁在工作树里，不是 /tmp：
  要防的正是「同一个工作树」；锁里记 pid，进程没了自动作废）；
  ②注入检查每条用例跑完立刻核对**注入还在不在**，
  被人动过就整轮作废、不落报告（`spec/verify/mutationLock.test.ts` 是它的缺陷回放）。
  拿不到锁时**直接拒绝启动**（退出码 2）并说清是谁占着 ——
  宁可这一轮不跑，也不产出一份不可信的结论。
- **跑过的验证，不等于对当前代码的验证（2026-11-05）** ——
  症状是两份「看起来都对」的证据对不上：
  注入报告写着「88 个用例，不合格 0 个」，追溯矩阵照抄这句话，
  而报告生成后的 20 分钟里就有 21 个源文件、1 个验证器被改过 ——
  **67 条结论已经对不上当前代码**，读的人完全看不出来。
  「没跑过的验证不是通过」这条只治了「没跑」；
  这里治的是「跑过，但跑的不是现在这一版」——
  「验证器抓得住这个错」是**某一版**验证器与**某一版**实现之间的结论，
  动过其中任何一边，它就不再自动适用于当前代码。
  修法三处：
  ①`spec/verify/mutation-check.ts` 的报告里记下**文件指纹**（sha256）
  与生成时间 —— 没有凭据，读者无从判断结论对应哪一版代码；
  ②`spec/verify/evidenceFreshness.ts` 逐条比对指纹，
  给出 fresh / stale / file-missing / unknown 四种判定；
  ③追溯矩阵 §2.4.1 把这批结论的适用范围**说清楚**，
  「实际验证了什么」那一条也带上限定语。
  关键的一条：**unknown ≠ fresh** —— 老格式报告没有指纹，
  说清不了对应哪一版代码，那就只能说「说清不了，就不能说它成立」，
  不能默认它还成立（`spec/verify/evidenceFreshness.test.ts` 是这一条的缺陷回放）。
  ①里记的指纹现在有**三样**：验证器、被改的源文件，以及验证器的**数据依赖**
  （运行时从磁盘读的黄金快照基线之类）—— 数据依赖的规则与主证据侧共用
  `spec/verify/dataDeps.ts`，否则同一个改动两边会给出两套话。
- **报过但现在跑不起来的验证，连报都没报过（2026-11-05）** ——
  症状比上一条更硬：质量引擎把扣分幅度搬进规则表（`qualityRules.ts`）之后，
  8 条 AC-QLT-* 注入用例的**锚点全部失配** —— 那 8 条用例**一条都跑不起来**；
  而全量报告里写着的仍然是「88 个注入用例，不合格 0 个」，
  追溯矩阵照抄这句话，整条证据链看上去毫无破绽。
  指纹那条治不了它：指纹只能告诉你「代码变了」，
  锚点失配则能告诉你「**这条结论现在确定不成立**」——
  注入执行不了，「验证器抓得住这个错」从来就没人验证过。
  修法三处：
  ①`spec/verify/mutation-check.ts` 把 `MUTATIONS` **导出**，
  并用 `import.meta.main` 守卫把跑批与定义分开（被 import 时绝不启动那十几分钟的跑批）；
  ②`spec/verify/anchorHealth.ts` 做一次**静态**三方对账（不注入、不起服务、不开浏览器，毫秒级）——
  定义 ↔ 报告 ↔ 当前代码：锚点命中且唯一吗？定义了但报告里没有的（还没进过全量证据）？
  报告里有但定义里没有的（孤儿）？
  ③追溯矩阵 §2.4.2 逐条点名，并明说这些条的「不合格 0 个」**不能算数**；
  「哪些结论仍不可信」与「实际验证了什么」两处也带上限定语。
  锚点**归文件所有者**修 —— 别人正在改的文件不要替他改锚点；
  看锚点健不健康用**干跑**：`MUTATION_CHECK_DRY_RUN=1 bun run spec/verify/mutation-check.ts`
  （只校验锚点，不注入、不改文件、不落报告，可以放心在共享工作树上跑）。
  修完锚点还要跑一次**子集**跑批（`MUTATION_CHECK_ONLY=AC-QLT-002,…`），
  证明新锚点确实落在被测路径上、验证器确实抓得住注入的错误 ——
  锚点「唯一」不等于「打在被测路径上」（`spec/verify/anchorHealth.test.ts` 是这一条的缺陷回放）。
- **跑过的验证，不等于对当前代码的验证 —— 主证据这边也一样（2026-11-05）** ——
  上一条治的是**注入报告**。可主证据（`spec/evidence/junit*.xml`）有同一个毛病，
  而且更常见：它记的是**每一次** PASS/FAIL。
  实测：`junit.xml` 生成于 02:00，之后领域内核的
  `qualityEngine.ts` / `layoutEngine.ts` / `textMetrics.ts` /
  `contentBinding.ts` / `layoutIntents.ts` / `index.ts` **六个文件**被改过，
  而矩阵照旧写着「PASS 65 / FAIL 0」—— 读者没有任何办法知道
  那 65 条 PASS 里有几条说的是**改之前**的那一版代码。
  主证据不能照抄注入报告的修法：junit 是 **Bun 的 reporter** 生成的，
  我们控制不了它的格式，**没有指纹可读**。
  所以换成两个拿得到的东西：
  ①**修改时间** —— 证据文件自己的 mtime 就是「跑批那一刻」；
  某个依赖文件的 mtime 比它新，就说明它在跑批之后被动过。
  mtime 的方向是**保守**的：碰过但内容没变也算变了 ——
  宁可多报过期，不漏报。**漏报才危险**：
  一条过期的 PASS 被当成当前代码的证明，比多报一条坏得多。
  ②**import 闭包** —— 「这条用例依赖哪些本地文件」不能靠猜：
  静态扫出验证器文件的本地 import，做传递闭包。
  修法三处：
  ①`spec/verify/verdictFreshness.ts` 给出 fresh / stale / unknown / file-missing 四种判定；
  ②追溯矩阵 §2.1.1 逐条点名「这批结论对应的是哪一版代码」，
  表按**验证器**归并（一个验证器管着十七条判据时合成一行）；
  ③「实际验证了什么」与「哪些结论仍不可信」两处带上限定语。
  两条边界必须写进矩阵，不能藏：
  · **E2E 的闭包里没有前端与服务端** —— Playwright 规格通过浏览器操作页面、
  通过 HTTP 打到服务端，它**不 import** 那些代码。
  所以 E2E 的依赖只能按**整条链**算（前端 + 服务端 + 领域内核），
  归因到文件级做不到 —— 这一点在 §2.1.1 里单独说明。
  · **unknown ≠ fresh** —— 本地 import 解析不到对应文件、
  或动态 import 的路径不是字面量，依赖就**扫不干净**；
  扫不干净就不能说「依赖的文件都没被改过」，只能判 unknown
  （`spec/verify/verdictFreshness.test.ts` 是这一条的缺陷回放）。
- **流水线说「全绿」的时候，它凭什么这么说（2026-11-05）** ——
  前面几条治的都是**证据**：证据旧了、证据说清不了、证据压根不存在。
  这次轮到**出口**：`spec/verify/all.ts` 的文件头写着
  「退出码：0 = 全链路通过；1 = 有环节失败」，
  而实现里判据执行与 E2E 两步的失败被标成「预期内」——
  **退出码仍然是 0**，终端还打印「✅ 工具链全绿」。
  也就是说：**判据不满足（覆盖率跌破 90%、E2E 挂了），
  在流水线的出口处没有留下任何痕迹**；
  而 `docs/testing-strategy.md` §7.1 写的是「Stage 2 任何失败 → 阻断、
  Stage 3 E2E 失败 → 阻断」，SPEC-GOV-001 写的是「覆盖率不足 → 阻断发布」。
  另一半同样要治：**「E2E 的服务起不来」也是退出码 0** ——
  没跑出结论被当成了验证通过。
  修法把退出码拆成三层：
  ①`spec/verify/pipelineVerdict.ts` 给出 0 / 1 / 2 三种判定；
  ②「有没有跑出结论」只看一件事：**这一步的结论证据是不是本轮产出的**
  （跑之前拍一次 mtime，跑完再拍一次，两次一样就是没产出）；
  ③`spec/verify/all.ts` 的每一步都声明自己产出哪份证据，
  判据执行 → `junit.xml`、E2E → `junit-e2e.xml`、
  注入检查 → `mutation-report.json`、追溯矩阵 → `traceability.md`。
  结构校验与类型检查**不产出结论** —— 它们失败就是「工具链坏了」，退出码 2。
  两条边界要说清：
  · **失败不中断后续步骤** —— 追溯矩阵必须照常生成，
  否则「为什么红」永远没人看得见。失败影响的是**退出码**，不是「还跑不跑」。
  · **「实现不满足判据」现在也要退出 1** —— 它不再是「预期内」。
    原来的区分没有消失，只是从**退出码**挪到了**措辞**上：
  红的是实现还是工具，看汇总里那一行就分得清。
  （`spec/verify/pipelineVerdict.test.ts` 是这一条的缺陷回放，
  里面还真的拉了子进程、写了真的证据文件。）
- **报告说「没有失败」，它凭什么这么说（2026-11-05）** ——
  前面几条治的都是**证据**：证据旧了、说清不了、压根不存在。
  这次轮到**报告的口径**：追溯矩阵 §2.2「失败明细」只列**挂了判据**的失败。
  一次跑批 337 个用例里只有 98 个被某条判据点名；
  另外 239 个用例要是挂了 —— §2.2 照常写「（无）」，
  而「是哪个用例挂了」全报告没有第二处提。
  （「实际验证了什么」那节给的是**计数**：N 个用例、M 失败 ——
  计数说得出"有失败"，但说不出"哪个失败"；
  而读者查失败时翻的正是「失败明细」那一节，那里说「没有」。）
  修法：`spec/verify/evidenceLedger.ts` 把整个证据集摊开对账 ——
  ①多少用例挂了判据、多少没挂；
  ②没挂判据的用例里有没有失败的，有就**逐条点名**（文件 + 用例 + 出处）；
  ③判据点名的验证目标有没有在证据集里找不到
  （找不到 → 那条判据一律 INCONCLUSIVE，绝不按「通过」算）。
  两条边界要说清：
  · **「FAIL 0」只数挂了判据的失败** —— 所以摘要里必须同时写明
    「没挂判据的失败 N 个」；否则读者看见 FAIL 0 就以为整轮都绿了。
  · **一个失败都没有的时候也要说得出依据** ——
    「（无）」得附一句「没有判据的 239 个用例也全都过了」，
    不能靠「没列」来暗示。
  （`spec/verify/evidenceLedger.test.ts` 是这一条的缺陷回放；
  另外还真的造了一份带失败的 junit 跑了两遍生成器 ——
  旧版写「（无）」，新版把那条失败点了名。）
- **矩阵说「有 2 条 FAIL」，流水线却说「生成追溯矩阵：通过」（2026-11-05，第 12 轮）** ——
  前面几条治的都是**证据**（旧了 / 说清不了 / 不存在）与**口径**（没点名）；
  这次轮到**出口**。
  追溯矩阵是**一份报告**：它逐条记下每条条款的 PASS / FAIL / INCONCLUSIVE，
  但**报告本身不拦人** —— 矩阵里写着 FAIL 2，而流水线末尾那一步照样显示
  **✅ 通过 生成追溯矩阵**。读的人只看见一行绿。
  这跟本项目治了一路的病是同一个：**结论没有出口**。
  修法：`spec/verify/releaseGate.ts` 给出闸门，矩阵生成器末尾执行它：
  ① **FAIL 一律不放行** —— 「已知欠账」不能拿来给 FAIL 开门，
    欠账是「还没做」，FAIL 是「做了但不对」（那是回归，不是债）；
  ② **INCONCLUSIVE 不放行**，除非它已登记在 `spec.yaml` 的 `known_gaps` 里
    —— 没跑过的验证不是通过；但**说得出为什么没做、打算什么时候做**的是明账，
    `known_gaps` 就是那张登记表；
  ③ **连判据都没有的条款**：已降级（`status` 不是 active）就放过；
    还是 active 又没登记 = **悬空条款** → 不放行
    （质量战略 波 3 ③：每条要么补判据，要么降级并写明原因）。
  闸门挡住时，矩阵生成器以**退出码 1** 收场 →
  流水线的退出码随之变成 1（「有结论，结论是不通过」）。
  矩阵里多出 **§2.7 发布闸门**，逐条写明谁挡住了放行、为什么。
  （`spec/verify/releaseGate.test.ts` 是这一条的缺陷回放：
  它复现的正是「矩阵写着 FAIL 2 / INCONCLUSIVE 1，而欠账只登记了其中一族」那一轮。）
- **「超时」不能报成「不通过」（2026-11-05，第 14 轮）** ——
  前面几条治的都是**证据**与**出口**。这次治的是**结论的说法**。
  追溯矩阵一直只有两档能用：「跑过」落进 PASS 或 FAIL。于是**超时也被报成 FAIL** ——
  也就是「实现不满足判据」。
  这条**假的确定结论**真出现过两次：
  ① `apps/api/tests/security/session-cookie.test.ts` 在流水线里耗时 **906.903 秒**、
  用例超时（限 5 秒）；隔离复跑 **5 条用例 3.2 秒全过** —— 环境被抢，不是实现坏了；
  ② E2E 链的 180 秒超时一次性报成 **916 秒** —— 机器进了 Maintenance Sleep
  （计时器不跑），也不是实现坏了。
  两次都被记成「实现不满足判据」——
  读的人（和下一轮的我）会去修一个**没毛病的验证器**。
  修法三处：
  ①`spec/verify/junit.ts` 读出 `<failure type="..."/>`（Bun 实测：
  超时 → `TimeoutError`，断言不通过 → `AssertionError`）与用时，
  并提供 `isTimeout()` / `failureBreakdown()` —— **两种红分开数**；
  ②`spec/verify/verdict.ts` 给出三档结论：
  **超时 → INCONCLUSIVE**（没跑出结论）、断言不通过 → FAIL、
  没跑过 / 不是 automated → INCONCLUSIVE；条款取最坏的一档
  （FAIL > INCONCLUSIVE > PASS）；
  ③流水线的措辞跟着分：只有超时时不再说「实现不满足判据」，
  改说「没跑出结论 —— 多半是环境被抢或机器睡眠，隔离复跑一次再判」。
  两条边界要说清：
  · **不是弱化校验** —— 超时的条款**照样挡住放行**：
    发布闸门对没登记的 INCONCLUSIVE 一律不放行（上一条）；
    流水线退出码仍然是 1。变的只是**结论的说法**：
    从「实现错了」改成「还不知道」。
  · **失败但没有类型 → 按断言不通过处理** ——
    判不出是超时就按最保守的一档记账，不许靠「说不清」蒙混过关。
  矩阵里多出 **§2.2「超时的用例（不是断言不通过）」**，
  逐条写明用时；不超时的段落照旧。
  （`spec/verify/verdict.test.ts` 与 `spec/verify/junit.test.ts` 是这一条的缺陷回放：
  里面原样重放了上面那两起假超时。）
- **「基线红」不能报成「验证器弱」（2026-11-05，第 15 轮）** ——
  第 14 轮治的是**超时**被报成「不通过」。这次治的是同一族的另一半：
  **注入检查**里，基线自己就没过的时候，被报成「验证器抓不住注入错误」。
  注入用例走三步：基线 PASS → 注入必须 FAIL → 还原后重新 PASS。
  以前这三步只有两档结论（`!baseline || !caught || !restored` 一律算「不合格」），
  然后整轮报：
  > ❌ 存在抓不到注入错误的验证器 —— 需要补强后才能声称这些判据有效。

  那次流水线里 AC-GOV-001 那一行是 `基线 ✗ / 抓到 ✓ / 还原 ✓` ——
  验证器**确实抓到了**注入，源文件**确实还原干净了**；
  只是**基线那一轮**里 `apps/api/tests` 有 19 条用例没过（抖的），
  于是整轮退出码 1，终端上写着「需要补强验证器」。
  同一份代码隔离复跑 → **91 个用例全过、不合格 0 个**。
  也就是说：报告把「环境抖了」说成了「验证器太弱」——
  而**假结论最贵的地方**就在这儿：读的人会去补强一个没毛病的验证器。
  修法：
  ①`spec/verify/mutationVerdict.ts` 给出三档结论（与判据侧同一套词）：
  **基线红 → INCONCLUSIVE**（没跑出结论）、基线绿但没抓到 → FAIL、
  抓到但没还原干净 → FAIL（源文件被改坏了）、全过 → PASS；
  ②注入报告每条多记一个 `verdict`，顶层多记 `inconclusive`；
  ③矩阵 §2.4 多一列「结论」，并且**基线红时不再声称
  「全部注入错误都被对应验证器抓到」** —— 那批结论对它们**不成立**；
  ④退出码分开：确定的坏结论 → 1；只有「没跑出结论」→ 2
  （`2` = 有环节没跑出结论，见 `verify/pipelineVerdict.ts` 的契约）。
  两条边界要说清：
  · **不是弱化校验** —— 基线红的用例**照样挡住放行**
    （退出码 2 → 流水线不放行）。变的只是**结论的说法**：
    从「验证器弱」改成「还不知道」。
  · **「抓到注入」那一栏在基线红时不可信** —— 注入后的那一轮本来也会
    因为同样的原因红，它红了**证明不了**什么。
  （`spec/verify/mutationVerdict.test.ts` 是这一条的缺陷回放：
  它原样重放了上面那一次基线抖动。）
- **注入结论靠「差分」，不靠退出码（2026-11-05，第 16 轮）** ——
  上一条治的是「基线红 → 验证器弱」。这一条治的是它**背后**的那个病根：
  判定用的三个量全是**退出码**，而退出码在「树本来就红」的时候
  **每一个都会说反话**：
  · 基线红 → 被记成「验证器抓不住」（**冤枉验证器**）
  · 注入那轮红 → 被记成「**抓到了**」（冤枉验证器的反面 ——
    给一个什么都没证明的验证器**记了功**）

  第 14 轮那次踩中的是第二种。**根因查实**（2026-11-05）：
  AC-GOV-001 的验证器是 `scripts/check-coverage.check.ts`，
  它的用例调的是 `main()` —— 而 `main()` 会**重跑整套测试**。
  于是这一条的「基线」量的是**整棵树健康不健康**，
  不是那个验证器健康不健康。别人在 `apps/api` 上改到一半，
  这一条的基线就红了。

  修法：判定改成**差分**。每一轮都记下「**哪几条**用例失败了」，
  然后只看两件事：「注入带来了哪些**新的**失败」、
  「还原之后还多出哪些失败」。

  | 观察 | 结论 | 说法 |
  |---|---|---|
  | 注入带来新失败，还原后回到基线 | PASS | 验证器抓得住这个错 |
  | 注入带来新失败，还原后仍多出 | FAIL | 没还原干净，或树被别人改了 |
  | 注入没带来新失败，基线是绿的 | FAIL | 验证器抓不住这个错 |
  | 注入没带来新失败，基线本来就红 | INCONCLUSIVE | 没跑出结论（**不是**验证器弱） |
  | 有一轮压根没跑出结论 | INCONCLUSIVE | 没跑出结论 |

  三件事要说清：
  · **不是弱化校验** —— 树是绿的时候，新旧两套判定**逐条相同**
    （`mutationVerdict.test.ts` 里有逐条对照的用例）。
  · **树本来就红不再是「验证器弱」的证据** —— 它被**记下来**
    （报告里逐条列出先红着的是哪几条），由**该管它的那一步**
    （判据执行）去挡住放行。
  · **「注入那轮红」不再自动等于「抓到了」** —— 红的**原因**必须对得上，
    否则什么都不许记功。

  顺带修掉两个「跑不出结论」被当成「跑过了」的坑（Bun 实测 2026-11-05）：
  · 测试文件**加载不了**（注入把 import 改坏了）→ Bun **根本不写 junit 文件**
  · `-t` 过滤**没匹配上**任何用例 → 退出码 1，而 junit 里每一条都是 `<skipped/>`

  以前这两种都长得跟「有东西坏了」一模一样。现在都记成「整轮失败」，
  差分照常算 —— 不再因为「什么都没跑」被判成「验证器扛住了注入」。

  **报告格式变了**（旧报告仍能读）：
  · 新：`baseline` / `mutated` / `restored` 三段，各带 `failed`（失败用例清单）
    与 `no_verdict`；顶层多一个 `reason`（这一条为什么是这一档）。
  · 旧：`baseline_pass` / `caught` / `restored_pass` 三个布尔量 ——
    读老报告走 `mutationVerdict.ts` 的 legacy 兜底，
    **不会**把一份好好跑过的报告误报成「没跑出结论」。

  **边界（说清，不藏）**：
  · **差分的粒度受限于「一轮观察得到几条用例」** ——
    当前全部注入用例都**按用例名过滤**跑单条用例（`wholeFile` 那个选项还留着，
    但**当前没有一条用例用它**），所以一轮观察里通常只有**一条**用例。
    差分分辨得出「**这一条**从绿变红」与「**这一条**一直红着」，
    分辨不出「注入弄坏的是不是就这一条」。
    **含义**：差分提高的是**证据的可核对性**（报告里写的是**事实**，
    不是三个「绿不绿」的布尔量），**不是归因的精度**。
  · 差分把「归因于注入」和「树本来就红」分开了，但**分不开「注入造成的」与
    「这一轮恰好抖了」** —— 一条只在注入那轮失败、又恰好是抖的用例，
    会被算成「注入造成的」。这是差分的固有代价；
    判据侧那套「超时 → 没跑出结论」的规矩治不了它
    （那套认的是**超时**，这里是**断言不通过**）。
  · 反过来也一样：一条只在还原那轮失败的抖动用例，会被报成「没还原干净」。
    两种误判都指向**同一个动作**：隔离复跑一次再判。
  · **这一版的证据**（提交 `5a2fc06`，对着 `5f809b8` 在隔离树里跑完整条流水线）：
    122 个注入用例**全部**是「基线失败 0 / 注入新增 1 / 还原新增 0」的差分结论，
    不合格 0 个 —— 其中包括第 14 轮那条曾经被记成「基线 ✗ / 抓到注入 ✓」的
    **AC-GOV-001**，现在两行都是「注入新增 1 条失败、还原后回到基线」。
    判据执行 462 pass / 0 fail，E2E 98 条 / 0 失败，全链路退出码 0。
    **注意**：这棵树的基线是**绿的** —— 差分在基线红的时候给的是
    「没跑出结论」，不是「通过」。
- **页序基线是 1-based，写在 `DEC-012` 里** ——
