## 1. 产品定位与技术命题

AI PPT Studio 不是"输入一句话，吐出一份 PPT"的生成式工具。它的技术定位是：

> **以结构化 Slide IR 为唯一真相、以确定性排版内核保证质量、以多 Agent 编排驱动内容生产的演示文稿工程平台。**

三条技术命题决定了整个架构：

| 命题 | 含义 | 架构后果 |
|---|---|---|
| **结构化优先** | 内容与几何分离，内容是数据，几何是计算结果 | 引入 IR 与 `SlideContent` 两级契约，AI 永不产出像素 |
| **确定性内核** | 版式、安全边距、碰撞检测、导出全部是纯函数 | 领域层零 AI 依赖，可单测、可快照、可复用 |
| **前后端同源** | 渲染与版式逻辑只有一份实现 | 抽出 `@ppt/core` 共享包，前端预览 = 后端导出 |

### 1.1 能力全景

```
                       ┌──────────────────────────────────┐
                       │        AI PPT Studio             │
                       └──────────────────────────────────┘
        ┌──────────────┬──────────────┬──────────────┬─────────────┐
        ▼              ▼              ▼              ▼             ▼
```

**分层规则（硬约束）**：

| 规则 | 说明 |
|---|---|
| 依赖方向单向向下 | 领域层不依赖任何上层，也不依赖任何 IO 设施 |
| 领域层零 AI | `@ppt/core` 不 import 任何模型 SDK，可离线单测 |
| 编排层不碰几何 | Agent 只产出内容结构，不接触 `Geometry` |
| 应用层无业务算法 | Controller 只做编排与校验，算法在领域层 |
| 体验层不含业务规则 | 前端不做质量判定与版式决策 |

### 2.2 代码到架构的映射

```
slider/
├── apps/
│   ├── web/            → ① 体验层    src/{app,features,components,core}
│   ├── api/            → ④ 应用层    src/{routes,services,middleware,db,jobs}
│   └── worker/         → ④ 应用层    src/{handlers,pipeline}
├── packages/
│   ├── core/           → ③ 领域层    types/ engine/ contracts/ assets/
│   └── adapters/       → ② 编排层    model/{gemini,anthropic,openai}/ renderer/
└── docs/
```

> `packages/adapters` 与 `packages/core` 分离，是为了让 core 保持零依赖——任何时候 core 都可以被单独拷进另一个项目。

## 3. 五条架构原则

| # | 原则 | 落地机制 | 违反的代价 |
|---|---|---|---|
| 1 | **IR 是唯一真相** | 项目状态 = `SlideIR` 集合；不存"第二份页面状态" | 前后端各自维护页面数据 → 必然漂移 |
| 2 | **确定性内核 / 概率外壳** | AI 只在编排层；领域层全确定性 | 让 AI 参与排版 → 输出不可复现、不可测试 |
| 3 | **前后端同源** | 版式/质量/渲染单一实现（`@ppt/core`） | 两份 layoutEngine → 预览与导出不一致 |
| 4 | **契约先行** | 一份 Zod schema 驱动 API 校验 + LLM 结构化输出 | 手工 JSON.parse → 模型多返一个字段就污染 IR |
| 5 | **异步优先** | 长任务（生成/导出）走队列 + SSE | 主线程阻塞 → 12 页导出卡死 UI |

## 4. 关键场景端到端时序

### 场景 A：从一句话到可编辑演示（核心链路）

```
用户        体验层            API 层          编排层         领域层        基础设施
 │           │                 │               │              │             │
 │ 输入需求   │                 │               │              │             │
 ├──────────►│ POST /ai/requirement              │              │             │
 │           ├────────────────►│               │              │             │
 │           │                 │──invoke──────►│              │             │
 │           │                 │               │─LLM调用─────►│             │
 │           │                 │               │              │             │
 │           │                 │◄──requirement─┤ Zod校验      │             │
 │           │◄──requirement──┤ 记账          │              │             │
 │           │                 │               │              │             │
 │ 大纲+槽位 │ POST /ai/outline                  │              │             │
 ├──────────►├────────────────►│──invoke──────►│              │             │
 │           │                 │               │─LLM调用─────►│             │
 │           │                 │               │  ↓            │             │
 │           │                 │               │ 产出 outline  │             │
 │           │                 │               │   + SlideContent            │
 │           │                 │               │  ↓ Zod校验    │             │
 │           │                 │               │  ↓ bindContent────────────►│
 │           │                 │               │              │ 槽位补全    │
 │           │◄──outline───────┤               │              │             │
 │           │                 │               │              │             │
 │ 编译页面  │ POST /projects/:id/compile        │              │             │
 ├──────────►├────────────────►│──apply─────────────────────►│             │
 │           │                 │               │   layoutEngine             │
 │           │                 │               │   8种版式 → SlideIR        │
 │           │                 │◄──slides─────────────────────┤             │
 │           │                 │──质量闸门────►│             │             │
 │           │                 │   evaluate────────────────────►│            │
 │           │                 │   Q<阈值 → 拒收/降级重试                       │
 │           │◄──SlideIR───────┤──持久化──────►│────────────►│ PG 写入     │
 │           │                 │               │              │             │
 │           │◄──SSE done──────┤               │              │             │
```

**架构要点**：

1. **两道闸门**——`Zod 校验`（结构合法）与 `质量闸门`（Q 分达标）。LLM 输出必须连过两关才能落库。
2. **`bindContent` 在编排层调用领域层**——槽位补全是确定性逻辑，不该由 LLM 猜。
3. **降级不落脏数据**——降级链触发时产出确定性内容（按 topic 动态生成，不再是写死的 Agent 架构大纲），且质量分仍受闸门约束。

### 场景 B：AI 改页（增量编辑）

```
用户选中文本框，输入"这段改成管理层视角"
 │
 ▼
前端只发送：{ slideId, instruction, targetElementId, mode,
              contentDigest, elementDigest }   ← 不传全页 IR
 │
 ▼
编排层：Editing Agent
 │   ├─ 构造 prompt（含该页内容槽位摘要 + 目标元素）
 │   ├─ LLM 返回 { patches: IRPatch[], message }
 │   ├─ Zod 校验 patch 结构
 │   └─ 施加前检查：几何越界？ID 冲突？operation 合法？
 │
 ▼
领域层 patchApplier
 │   ├─ update_element / add_element / remove_element
 │   ├─ replace_group / restyle_slide / reorder_elements
 │   └─ 输出新 SlideIR
 │
 ▼
质量闸门：复评四维分
 │   ├─ 分数未下降 → 接受，写 slide_versions（含 patch 留痕）
 │   └─ 分数下降超阈值 → 回滚，换更严格 prompt 重试一次
 │
 ▼
返回 { slide, versionId, message }  →  前端刷新选中元素
```

**架构要点**：

- **上下文裁剪**是这里最重要的优化：只传内容槽位摘要，不传几何与样式，token 降一个量级，且模型不会误改几何。
- **Patch 而非全量**：模型改一个卡片不必重写整页 30 个元素。
- **质量闸门内建在编辑链路里**，不是事后可选的"检查按钮"。

### 场景 C：导出（服务端管线）

```
前端点击"确认导出 PPTX"
 │
 ▼ POST /api/exports { projectId, format:'pptx', scope:'deck' }
 │
 ▼ API：创建 job（status=queued）→ 返回 jobId
 │
 ▼ 前端 EventSource 订阅 /api/exports/:id/events
 │
 ▼ Worker 领取（FOR UPDATE SKIP LOCKED）
 │   ├─ 取项目 SlideIR + TemplateIR
 │   ├─ 逐页：SlideIR → SVG（@ppt/core/svgRenderer）
 │   ├─ resvg 注册本地字体 → 光栅化（仅 PDF/PNG 需要）
 │   ├─ pptxgenjs：IR → 原生形状/文本框 → .pptx
 │   ├─ 写入对象存储 → artifacts 表
 │   └─ SSE 推进度 { stage, page, total, percent }
 │
 ▼ SSE: event done { downloadUrl, expiresAt }
 │
 ▼ 前端 a[download] 触发下载（预签名 URL，7 天有效）
```

**架构要点**：

- **进度可感知**：12 页导出不是黑盒，用户能看到"第 7 / 12 页"。
- **产物与源数据解耦**：导出物独立存储、独立过期，不污染项目数据。
- **可编辑性保真**：PPTX 走原生形状映射，下载后能在 PowerPoint 里继续改——这是与"导出成图片"的产品级差距。

## 5. 领域模型

### 5.1 IR 三层管线（架构的中枢）

```
┌─ L1 需求层 ──────────────────────────────────────────────┐
│  PresentationRequirement { topic, purpose, audience,      │
│    pageCount, style, depth, aspectRatio }                │
│    来源：人工表单 + AI 抽取                                │
└───────────────────────┬───────────────────────────────────┘
                        ▼
┌─ L2 叙事 + 排版层 ───────────────────────────────────────┐
│  SlideOutlineItem { title, purpose, keyMessage,           │
│    bulletPoints, speakerNotes, layoutPreference }         │
│         +                                                │
│  SlideContent { bullets, layers, columns, metrics,        │
│    phases, radial, summary, meta }   ← 版式槽位契约        │
│    来源：AI 产出 + 人工编辑 + contentBinding 补全          │
└───────────────────────┬───────────────────────────────────┘
                        ▼
┌─ L3 像素层 ──────────────────────────────────────────────┐
│  SlideIR { canvas, layout, elements: SlideElement[] }    │
│    每个元素含 Geometry（x/y/w/h/rotation）与 ElementStyle  │
│    来源：layoutEngine 纯函数计算，AI 永不介入              │
└───────────────────────────────────────────────────────────┘
```

**这条管线的分界线就是产品的质量承诺**：AI 到 L2 为止，L2 → L3 是确定性计算。

### 5.2 实体关系

```
users ──┬── sessions
        │
        ├──< projects ──┬──< slides ──< slide_versions
        │               │              (snapshot + patch)
        │               ├──< documents        (上传素材)
        │               ├──< artifacts        (导出产物)
        │               └──  qualityReport (JSONB 内嵌)
        │
        ├──< templates  (builtin / user / extracted)
        └──< jobs ──< artifacts
                └── model_calls (成本与效果记账)
```

**建模取舍**：

| 数据 | 形态 | 理由 |
|---|---|---|
| `outline` | JSONB | 整体重写的数组，关系化无收益 |
| `slides` | 关系表 + JSONB `ir` | 逐页编辑、需索引、需版本 |
| `template` / `requirement` | JSONB 内嵌项目 | 与项目 1:1，读时整体取 |
| `slide_versions.snapshot` | JSONB | 回滚需要完整 IR，拆表无收益 |
| `slide_versions.patch` | JSONB | 审计与重放需要可读的补丁序列 |
| `model_calls` | 关系表 | 需按时间/用户/Agent 聚合查询 |

### 5.3 元素模型

```ts
SlideElement {
  id, type, role, content, geometry, style, editable, parentId?, groupId?, zIndex, metadata?
}
//     ↑       ↑      ↑
//     │       │      └── 语义角色：title/card/layer/metric/badge/divider/footer...
//     │       └───────── 几何类型：text/card/architecture_layer/metric/badge/shape/group
//     └───────────────── 稳定 ID：patch 寻址、版本对比的锚点
```

`role` 是**语义锚点**——模板切换、主题重映射、质量检查都按 `role` 分类处理，这是整个系统可扩展性的关键（新增版式不需要改主题逻辑）。

## 6. 数据架构

### 6.1 数据分类与生命周期

| 类别 | 内容 | 存储 | 生命周期 |
|---|---|---|---|
| **事务数据** | 用户、会话、项目元信息 | PostgreSQL | 长期（可删除） |
| **内容数据** | SlideIR、大纲、版本、素材 | PostgreSQL JSONB + 对象存储 | 随项目；版本保留 90 天 |
| **产物数据** | PPTX/PDF/PNG 导出物 | 对象存储 | **7 天**（TTL 自动清理） |
| **遥测数据** | 模型调用、指标、日志 | PG / Prometheus / 日志系统 | 日志 30 天；记账长期 |

### 6.2 一致性边界

| 数据 | 一致性要求 | 机制 |
|---|---|---|
| 项目与幻灯片 | 强一致 | 单库事务 |
| 幻灯片并发编辑 | 乐观锁 | `versionId` 比对，冲突返回 409 |
| 导出产物 | 最终一致 | 异步任务 + 幂等键 `(jobId, format)` |
| 模型调用记账 | 最终一致 | 异步写入，不阻塞主流程 |
| 页面预览 | 弱一致 | 客户端乐观更新 + 服务端确认后校正 |

### 6.3 前端状态策略（演进后）

```
┌─────────────────────────────────────────────────────────┐
│ Server State (TanStack Query)                            │
│   项目列表 · 项目详情 · 幻灯片 · 版本 · 模板 · 导出任务   │
│   → 缓存 / 重试 / 失效重取 / 乐观更新                    │
├─────────────────────────────────────────────────────────┤
│ Client State (Zustand)                                   │
│   当前选中元素 · 缩放 · 撤销栈 · 面板开合 · 主题开关     │
├─────────────────────────────────────────────────────────┤
│ Ephemeral (React useState)                               │
│   输入框内容 · 加载态 · 临时提示                          │
└─────────────────────────────────────────────────────────┘
```

> **当前状态**：项目数据在 `localStorage`，编辑态在 React state，撤销栈在 `Workbench` 内存 → 刷新全丢、无法协作。
> **演进后**：服务端为准，TanStack Query 承载缓存与乐观更新，Zustand 只留纯客户端状态。

## 7. AI 能力架构

### 7.1 Agent 拓扑

```
                         ┌──────────────────┐
                         │   ModelRouter    │

        │Gemini    │      │Anthropic │       │OpenAI    │
        │主 · 快/多模态│      │备 · 强推理│       │兼容端点  │
        └──────────┘      └──────────┘       └──────────┘

   ┌──────────────────────────────────────────────────┐
   │  Requirement Agent   Outline Agent   Editing Agent │
   │       抽取需求          叙事+槽位       增量补丁      │
   │                                                    │
   │              Extractor Agent（视觉/OOXML）           │
   └──────────────────────────────────────────────────┘
              │                    │
              ▼                    ▼
      ┌───────────────┐    ┌──────────────┐
      │  Zod 输出校验  │    │  质量闸门     │
      │  (结构合法性)  │    │  (Q 分阈值)   │
      └───────────────┘    └──────────────┘
              └────────┬─────────┘
                       ▼
                  @ppt/core
```

### 7.2 降级链

```
primary 模型 ──失败──► secondary 模型 ──失败──► 确定性本地实现
      │                        │                        │
   429/5xx                   超时/空响应              始终可用
      │                        │                        │
   指数退避重试 ×2          指数退避重试 ×2          按 topic/版式
                                                       动态生成
```

**降级实现的硬约束**：本地实现必须按 `requirement.topic` **动态生成**，不能像现状那样对所有主题返回同一份"企业 AI Agent 技术架构规划"大纲。

### 7.3 质量闸门（生成 → 落库的唯一通道）

```
LLM 输出
   │
   ├─▶ Zod Schema 校验 ──失败──▶ 输出修复重试 ×2 ──仍失败──▶ 降级链
   │       通过
   ▼
内容槽位绑定（bindContent，领域层）
   │
   ▼
版式编译（layoutEngine，领域层）
   │
   ▼
质量评估（qualityEngine，领域层）
   │
   ├─ Q ≥ 阈值 ──▶ 落库 + 记账
   │
   └─ Q < 阈值 ──▶ 降级内容 / 重新生成 / 拒绝并提示
```

**闸门是架构组件，不是 UI 功能**。这保证无论内容从哪来（AI 生成、人工导入、模板提取），落库的都是达标内容。

### 7.4 评估闭环

```
20~30 个真实 case（含中英、含长文档、含边缘输入）
        │
        ▼
  ┌───────────┐   结构合法率 ≥ 99%
  │ 在线评估  │   槽位完整率 ≥ 95%
  │ (定期跑)  │   版式匹配率 ≥ 95%
  └─────┬─────┘   平均 token / 耗时 / 成本
        │
        │ 录制响应
        ▼
  ┌───────────┐   不烧 API 额度
  │ 离线回放  │   进 CI 每次提交跑
  │ (CI 跑)   │   Prompt 改动即回归
  └───────────┘
```

### 7.5 成本模型

| 场景 | 模型档位 | 相对成本 | 备注 |
|---|---|---|---|
| 需求抽取 | 快模型 | 1× | 输出小、结构固定 |
| 大纲生成（6 页） | 快模型 | 3× | 主要开销；Prompt 缓存可降 |
| 单页编辑 | 快模型 → 强模型 | 2× | 上下文已裁剪，很便宜 |
| 模板提取（视觉） | 强模型 | 10× | 高频低量，需配额限制 |
| 整本导出 | 零模型 | 0× | 纯计算 |

成本记账写入 `model_calls`，按 `用户 × 项目 × Agent` 三维聚合，配额超限返回 `QUOTA_EXCEEDED`。

## 8. 渲染与输出架构

### 8.1 渲染层次

```
SlideIR ──► svgRenderer ──► SVG DOM（元素保留 id，便于调试与 diff）
                │
      ┌─────────┼────────────┬──────────────┐
      ▼         ▼            ▼              ▼
   浏览器     resvg        pptxgenjs     pdf-lib
   直接渲染   (纯 Rust)    (原生形状)     (页容器)
      │         │            │              │
   实时预览   PNG/JPG      .pptx 可编辑   .pdf
```

**一条渲染源，三种输出目标**。SVG 是中间格式，所以：
- 预览所见 = 导出所得（同一份 SVG 生成逻辑）
- PPTX 走独立映射（因为要可编辑，不能用图）
- PDF 走位图嵌入（因为要保证中文字体不依赖阅读器）

### 8.2 字体与主题资源

```
packages/core/assets/
├── fonts/           Manrope · Plus Jakarta Sans · JetBrains Mono · Noto Sans SC
├── themes/          6 套内置主题的 Token 定义
└── templates/       母版规范（页眉页脚页码）
```

**约束**：全部 vendored 进仓库，构建时下载，运行时**不拉外网**。
原因：`svgRenderer` 现在依赖 Google Fonts `@import` —— 这在浏览器里能工作，在服务端完全失效，中文会全部回退。

### 8.3 导出路径选择

| 场景 | 路径 | 理由 |
|---|---|---|
| 工作台实时预览 | 客户端 SVG | 零延迟 |
| 单页 PNG/SVG | 客户端 canvas | 轻量 |
| 整本 PDF/PPTX | **服务端** | 字体保真、内存可控、不卡 UI |
| 模板预览图 | 服务端 | 与最终效果一致 |

### 9.1 当前结构的问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 组件过重 | `Workbench.tsx` 2080 行，混合编辑/渲染/AI/版本/主题 | 改一处要读全文 |

| 状态无分层 | 项目在 localStorage，编辑态在 useState，撤销在内存 | 刷新即丢 |
| 契约手写 | 前端自建 `SlideIR` 类型 | 与后端可能漂移 |

```

├── app/                    # 路由、布局、全局 Provider
├── features/               # 按业务能力切分（不是按组件类型）
│   ├── creation/           # 需求输入 + 模板选择
│   ├── outline/            # 大纲编辑
│   ├── workbench/          # 幻灯片编辑（拆为 canvas/inspector/ai-panel/history）
│   ├── templates/          # 模板库 + 提取
│   ├── quality/            # 质量报告
│   └── export/             # 导出
├── core/                   # 前端基础设施
│   ├── api/                # 生成的 API client（类型来自 @ppt/core 契约）
│   ├── hooks/              # useProject / useSlides / useExportJob
│   └── render/             # SVG 渲染封装 + 虚拟化
└── shared/                 # 通用 UI 组件
```

### 9.3 关键设计

| 关注点 | 方案 |
|---|---|
| **API 类型安全** | Zod schema → OpenAPI → 生成的 client，前端零手写接口类型 |
| **大页面渲染性能** | SVG 元素数可能过千 → 分层渲染（背景层静态、内容层增量）+ 只重渲染变更元素 |
| **拖拽流畅度** | 拖拽期间本地 transform，释放后提交服务端（节流 100ms） |
| **撤销/重做** | 客户端保留轻量栈（快速响应），服务端存权威版本（可跨设备） |
| **实时协同** | 预留 SSE 通道 + `versionId` 冲突提示；不引入 CRDT（成本过高） |

## 12. 架构决策记录（ADR）

> 每条记录：背景 → 决策 → 放弃的备选 → 后果。完整讨论见对应文档。

### ADR-001 · 抽取 `@ppt/core` 共享包，而非前后端各自维护
- **背景**：`SlideIR` 是中枢类型，但只在前端。后端要生成页面、要做服务端导出、要做质量校验，必然要复制一份 877 行的 `layoutEngine`。
- **决策**：建 `packages/core`，前端 `import from '@ppt/core'`，后端同源。
- **备选**：① 复制代码（放弃）② 后端只通过 HTTP 调前端渲染服务（放弃：多一跳且无法批处理）③ 代码生成器同步（放弃：复杂度高于收益）。
- **后果**：预览与导出必然一致；代价是包发布需兼顾两个消费方，用独立版本号管理。

### ADR-002 · 引入 `SlideContent` 槽位契约，让 AI 内容真正进入版式
- **背景**：现状 8 种版式中 7 种内容硬编码，用户生成的 AI 大纲**不会出现在渲染结果里**。
- **决策**：定义 `SlideContent`（bullets/layers/columns/metrics/phases/radial/summary/meta），版式按槽位消费；缺失时由 `bindContent` 从大纲确定性补全，**任何路径都不得回落到硬编码演示文案**。
- **备选**：① 让 LLM 直接产出 SlideIR（放弃：几何不可控、不可测）② 每种版式写一套 Prompt（放弃：维护成本爆炸、版式一改就要改 Prompt）。
- **后果**：版式与内容解耦；新增版式只需定义槽位消费规则，不影响 Agent。

### ADR-003 · AI 只产出内容，版式由确定性内核计算
- **背景**：产品宣称"确定性工程质量守卫"，但当前编辑链路已让 AI 返回几何相关字段。
- **决策**：编排层（LLM）只产出 L1/L2；L2→L3 全在领域层纯函数。编辑 Agent 改为只返回 `IRPatch`。
- **备选**：让 AI 输出完整 SlideIR（放弃：幻觉坐标、不可复现）。
- **后果**：输出可复现、可快照测试；代价是 Prompt 要更精确地描述槽位语义。

### ADR-004 · 用增量 `IRPatch` 取代全量元素覆写
- **背景**：`IRPatch` 类型早已定义却从未使用；`/api/ai/edit-slide` 返回全量元素数组。
- **决策**：Agent 返回 `{ patches: IRPatch[], message }`，后端 `patchApplier` 统一施加并校验。
- **备选**：继续全量（放弃：token 成本高、易误伤无关元素、无法审计）。
- **后果**：token 降一个量级、可审计、可回放；代价是 patch 校验逻辑要写扎实。

### ADR-005 · 一份 Zod Schema 同时驱动 API 校验与 LLM 结构化输出
- **背景**：现状是 `JSON.parse(text)` 直接进响应，无任何校验。
- **决策**：`z.toJSONSchema()` 生成 JSON Schema → Gemini `responseSchema` / Anthropic `tool.input_schema`；响应侧再用同一 schema 校验。
- **备选**：① 手写 JSON Schema（放弃：与 TS 类型双写漂移）② 依赖厂商 SDK 的类型（放弃：跨厂商不通用）。
- **后果**：契约单一来源、跨厂商统一；代价是 schema 变更需同步前端类型。

### ADR-006 · 导出下沉服务端，而非纯浏览器
- **背景**：现状 `jspdf` 默认字体不含 CJK → 中文 PDF 大概率乱码；`pptxgenjs` 在主线程跑 12 页会卡死 UI。
- **决策**：服务端 SVG → resvg → pdf-lib / pptxgenjs，产物入对象存储 + 预签名 URL；前端保留单页 SVG/PNG 快路径。
- **备选**：① 纯前端修字体（放弃：内存与兼容性问题无法根治）② 全服务端（放弃：单页导出也要等网络）。
- **后果**：中文保真、UI 不阻塞；代价是引入对象存储与任务队列。

### ADR-007 · 自研 ModelRouter 抽象，不直接调用厂商 SDK
- **背景**：现状硬编码 `model: 'gemini-3.8-flash'` 与单例 client，无重试、无降级、无记账。
- **决策**：统一 `ModelRequest/ModelResponse` 接口 + 能力路由 + 降级链 + 统一记账。
- **备选**：① 绑定单一厂商（放弃：无降级、无议价能力）② 引入 LangChain（放弃：抽象过重、Python 生态与 Bun 不合）。
- **后果**：可换模型、可降级、成本可归因；代价是多一层适配代码。

### ADR-008 · PostgreSQL 单库 + JSONB 混合建模，不引入 Redis
- **背景**：需要事务数据、JSON 文档、任务队列三种存储。
- **决策**：事务与文档用 PG（关系表 + JSONB 混合）；队列用 PG 表 + `SKIP LOCKED`。
- **备选**：① Redis + BullMQ（放弃：多一个中间件依赖，队列规模未到需要）② 专用文档库（放弃：项目数据本就强关联）。
- **后果**：运维面收敛到单一有状态依赖；代价是高吞吐队列场景需要迁 Redis。

### ADR-009 · 渲染字体 vendored 进仓库，不运行时拉外网
- **背景**：`svgRenderer` 依赖 Google Fonts `@import`，服务端渲染时该 import 无效。
- **决策**：字体文件进 `packages/core/assets/fonts`，构建时下载、运行时本地注册。
- **备选**：运行时从 CDN 拉（放弃：生产不稳定、外网依赖违反安全约束 SEC-13）。
- **后果**：渲染确定性；代价是仓库体积增加约 10MB。

### ADR-010 · 版本历史由服务端权威存储，客户端仅保留轻量撤销栈
- **背景**：现状 `versions` 字段全项目只有 `{}` 初始化，前端用内存 undo 栈，刷新即丢。
- **决策**：`slide_versions` 表存快照 + patch；客户端撤销栈只做即时反馈。
- **备选**：① 只用客户端栈（放弃：不可跨设备、不可审计）② 事件溯源全量事件（放弃：复杂度过高）。
- **后果**：可跨设备回滚、AI 编辑可追溯；代价是每次写操作多一次快照写入。

### ADR-011 · 服务端渲染去 `foreignObject` 化，卡片正文改用原生 `<text>`/`<tspan>`
- **背景**：`svgRenderer` 把卡片正文放在 `<foreignObject>` + XHTML `<div>` 里。浏览器支持，但 **`@resvg/resvg-js` 直接丢弃** —— 服务端光栅化会产出"只有空卡片框、没有任何文字"的 PPT，且**不报错**。
- **决策**：`@ppt/core` 的渲染器改为原生 SVG 文本排版（`<text>` + `<tspan>`），文本换行与截断由渲染层自研；浏览器内联与服务端共用同一份实现。
- **备选**：① 双渲染器（放弃：两套逻辑漂移，测试成本 ×2）② 引入 headless Chromium 做 HTML→SVG（放弃：~300MB 依赖，与"纯 Bun 轻量"目标冲突）。
- **后果**：服务端出图与 PPTX 导出共享同一套文本排版结果，格式间一致；代价是失去 flex/grid 布局能力，需自研文本折行算法。约束测试见 `test-cases.md` TC-EXP-006 / TC-EXP-009。

### ADR-012 · 版式专属元素 ID 统一加 slideId 前缀
- **背景**：现状 `grid_card_0` / `kpi_card_0` / `problem_box` 等版式元素 ID **不含 slideId**，同版式出现在两页时 ID 完全重复 —— 质量引擎跨页累积扣分（structure -5/次），且"精准编辑"按 elementId 定位会命中错误页的元素。
- **决策**：`@ppt/core` 生成的所有元素 ID 形如 `{role}_{slideId}_{localIndex}`，全局唯一是**契约**而非巧合。
- **备选**：① 保持现状（放弃：编辑定位错误是功能级缺陷）② 只在 `autoFixProject` 里修（放弃：修复前仍然错，且会破坏渲染器对 ID 语义的依赖）。
- **后果**：编辑定位可靠、质量分不再被跨页重复污染；代价是快照基线需要重建（64 组），且 `svgRenderer` 里 `el.id.includes('problem')` 这类**基于 ID 字符串的语义判断必须改为显式字段**（见 ADR-018 的 `SlideElement.variant`）。

### ADR-013 · 不引入 slides-master 作为运行时依赖，但采纳它的 DPI 语义
- **背景**：`slides-master`（.NET 9 / Open XML SDK）是社区里成熟的 SVG↔PPTX 转换实现，看上去可以直接替掉本项目的 `pptxgenjs` 导出链路。实测（本项目真实 SVG，21 个文本运行）后发现它会丢加粗（`font-weight` 400/500/600/700 → 21 个 `<a:r>` 里 0 个 `b="1"`）、丢换行（4 个 `<tspan>` → 0 个 `<a:br/>`，PowerPoint 并排成一行）、无 `<a:ea>`（CJK 字体无声明）、无 notesSlide —— 后者直接违反 SPEC-EXP-002。它也没有文本排版引擎，本项目的折行/截断（ADR-011 自研的那套）无处安放；部署侧还要多带一套 .NET 运行时与 libgdiplus 硬依赖。
- **决策**：**不引入 slides-master 作为运行时依赖**，SVG→PPTX 继续用 `pptxgenjs`。但**采纳它的 DPI 语义**：SVG 不携带分辨率，CSS 默认 96 DPI，而本项目设计画布 1920×1080 铺满 12192000 EMU 的幻灯片意味着 **1 设计 px = 6350 EMU = 0.5pt**；这个换算收敛到 `packages/core/src/engine/typography.ts` 单一真相源，SVG 渲染与 PPTX 导出共用。同时把 slides-master 的 `ConversionOptions.Dpi`（原本是死字段）实现成真开关并验证 —— 144 DPI 时 1920 画布正好铺满 13.33in 幻灯片。
- **备选**：① 整体换成 slides-master（放弃：丢加粗/换行/CJK 字体/备注，且引入异构运行时）② 把它当 .NET 侧车服务（放弃：保真损失照旧，却多一跳网络与一套进程编排）③ 换成 slides-master 的 SVG 生成（放弃：它没有排版引擎，等于重写本项目的折行算法）。
- **后果**：导出链路保持单一技术栈（ADR-006 的服务端导出结论不变），且**当场查出了本项目自己的一个 bug** —— `exportEngine.ts` 用 CSS 的 96dpi 系数 `px * 0.72` 换算字号，而设计画布下应是 `px * 0.5`，导致导出比预览大 44%～100%，同一份 IR 两种样子（已修，见 `typography.ts`）。代价是 `<a:br/>`、`<a:ea>`、字体栈 fallback 这三件 slides-master 也没做到的事要自己写；slides-master 退化为**建模参照物**与**上游修复的落点**（同一个 GitHub owner）。完整评估见 [`slides-master-integration.md`](./slides-master-integration.md)。

### ADR-014 · 一键修复只修真问题；诊断与修复能力分开声明
- **背景**：「一键合规修复」这个功能里有三处**看起来在做事、其实在做坏事**的地方，都是同一类病 —— **界面上的承诺比实现多**。
  1. **修复会把文稿改坏**。旧 `autoFixProject` 是无差别归一化：给每个元素重写 ID、把每个非背景元素钳进安全区。母版页码 (1760,1015,80,30) 与页脚 (100,1015,600,30) 本来就贴着画布下沿 —— 它们在画布内、只是不在**内容安全区**内，版式就是这么设计的；被钳进安全区等于每点一次「一键修复」，每一页的页码与页脚就上移 95px、左移 140px。ID 那边更隐蔽：旧实现把 ID 洗成 `{元素类型}_{slideId}_{序号}`，抹掉了 `header_` / `accent` 这类**语义前缀** —— 而渲染分层靠 `header_` 决定 kicker 走哪个层、前端主题重映射靠 `header_` / `accent` 决定配色，洗掉前缀等于让元素掉出模板层、换模板时不再跟随 accent 色。
  2. **`fixAction` 许诺了做不到的事**。每条诊断都写着「重命名为唯一 ID」「网格自动对齐重排」，但网格重排根本没实现 —— 用户点「一键修复」，什么都没发生，还被告知「已修复」。
  3. **侧边栏那个 92 分是安慰剂**。`qualityReport?.overallScore ?? 92` —— 没有体检报告时显示一个写死的 92 分。而服务端的 `quality_report` 列在正常流程里**恒为 NULL**（前端从不调 `/api/quality/evaluate`），所以「没有报告」本就是常态，那 92 分是一个从没体检过的文档的体检结果。
  4. 顺带在渲染层查到第四处：`renderBlock` 里判断「这是不是一整段原文」只看行数（`lines.length === 1`），而 `lines` 是**已经按盒高截断过**的 —— 原文折成 2 行、盒高只够 1 行时，截断被绕过，整段原文被塞进单个 `<text>` 横向溢出页面，而且不带省略号。
- **决策**：
  1. **越界的判据取画布边界（1920×1080），不是内容安全区**。只有真越出画布的元素被挪回安全区；**修复前没有越界的元素，一个坐标都不许动**。挪动时优先保持原尺寸 —— 缩窄不解除重叠，平移至少把它放回能看见的地方。
  2. **ID 重排保留语义前缀**，只改后半截（`header_s1` → `header_s1_1`，不是 `text_s1_1`）。前缀承载语义，不能洗。
  3. **修复后复评，任一维度分数不得低于修复前** —— 即「修复后复评、不更差才生效」；修坏了就整体退回（返回未修改的文稿）。宁可不修，也不能修坏。
  4. **决策**：诊断与修复能力必须分开声明 —— 只有真做了自动修复的规则才置 `fixable: true`。逐条清单：`struct_dim_*`（画布尺寸）、`struct_id_*`（ID 唯一）、`vis_bounds_*`（越界）可自动修；`vis_collide_*`（卡片碰撞）、`content_title_*`（缺标题）、`content_keymsg_*`（缺核心结论）、`consist_count`（页数不足）、`consist_cover`（缺封面）不可自动修 —— 它们的 `fixAction` 一律写成「建议人工调整…」。前端据此禁用按钮，不给用户「点一下什么都没变」的失望。（完整规则清单与后补的三条规则见 ADR-015 与 [`quality-rules.md`](./quality-rules.md)。）
  5. **质量分如实显示**：拿不到报告就不显示徽章，不给安慰剂。要显示就显示**真算出来的**分（前端用与服务端同一份 `@ppt/core` 在本地算）。
  6. **截断判据看内容，不看行数**：`lines.length === 1 && lines[0] === block.text`。
- **备选**：① 一键修复继续做无差别归一化（放弃：会把好文档改坏，而「一键修复」是用户对质量工具最直接的信任）② 保留承诺文案、补齐所有未实现的修复动作（放弃：网格重排与内容建议属于波 1 的工作量，且不是所有问题都能自动修 —— 「补一句核心结论」只有人能做）③ 保留写死的 92 分（放弃：安慰剂比没有分数更糟）④ 把版式语义从 ID 前缀搬到显式字段（放弃在本次做：涉及 64 组快照重建与全链路改造，属于波 2；本次只保证**不再破坏**前缀，语义搬迁另立 ADR —— 后由 ADR-018 落地）。
- **后果**：修复动作与诊断结论**一一对应**且**可验证**（SPEC-QLT-009 ~ SPEC-QLT-012 四条新判据锁住「只动坏的」「保住前缀」「不更差」「必须声明」）。代价是质量引擎的规则从此分成「可自动修」与「只能建议」两类，前端多一个字段要读；`fixAction` 的文案从「动作」改成「建议」，是用户可见的行为变化（按钮对不可修项变灰并给出原因）。本条只是**止血** —— 语义搬迁（ID 前缀 → `SlideElement.variant`）由 ADR-018 落地，见 [`quality-strategy.md`](./quality-strategy.md) 的波 2。

### ADR-015 · 扣分幅度的真相源是规则表，不是引擎里的字面量

- **背景**：ADR-014 解决了「修复会做什么」，但没解决「**质量分凭什么这么算**」。质量引擎里是这样写的：
  ```ts
  totalStructurePenalties += 15;   // ← 「15」的唯一依据是「代码里写的是 15」
  ```
  于是每一条质量判据都只能**自证**（oracle tier = `self-derived`）：验收用例断言「结构分等于 85」，而「85」从哪来？——「因为代码扣 15」。文档与实现谁对谁错没人说得清，改一个数字也没有任何东西会报警。这个漏洞在 M1（判据外部化率）上表现为 85 条判据里有 7 条是自证的 —— 7 条全部集中在质量引擎。
  与 ADR-014 同源：又是**承诺的比实现多**，只不过这次承诺的是「这个分数是有依据的」。
- **决策**：
  1. **扣分幅度搬进一张规则表**（`packages/core/src/engine/qualityRules.ts` 的 `QUALITY_RULES`），评分器退化成它的**解释器** —— 引擎里不再出现任何 `+= 15`。
  2. **规则表的真相源是文档**（[`quality-rules.md`](./quality-rules.md)），`qualityRules.ts` 是它的机器副本。两种漂移都要挡住：表多一行、文档少一节、或幅度对不上，验收用例必须失败（`spec/verify/quality-rules.test.ts` 逐行比对）。
  3. **规则 id 与诊断 id 一一对应**：规则的 `id` 是诊断 id 的前缀（`struct_dim_${slideId}`、`vis_bounds_${el.id}`…），全局性诊断（页数不足、缺封面）用规则 id 本身。界面上每一条问题都能顺着 id 找到文档里的对应小节。
  4. **补三条至今没有的规则** —— 它们正是「数据正确」与「PPT 好」的交界，此前完全看不见：
     - `content_thin`（非封面页至少要有一个实质内容件）与 `content_dup`（跨页核心结论不得重复）—— 内容分此前只查「有没有标题 / 结论」，查不出「空话页」与「同一句话说三遍」；
     - `vis_sparse`（承载信息的内容不得只盖住版心 20% 以下）—— 视觉分此前只查越界与碰撞，查不出「大片留白、像没排完」。
  5. **新规则的阈值必须实测标定，不许拍脑袋**：`vis_sparse` 的 20% 来自「真实版式覆盖率 30.8%–82.2%，只有标题的页面 9.5%」的实测；密度用**矩形并集**而不是包围盒或面积之和（后者分别高估到 53.6% 与 137.9%）。
  6. **原幅度予以追认，但追认这件事必须写在纸上**：原先那 8 条规则的幅度确实来自现状实现，不是独立推导出来的 —— 本条把它们**追认为契约**（与 ADR-014 追认 F7「原样搬到后端」的做法一致），并在文档里逐条写明理由与边界。追认不等于它们有独立证据，所以这些判据的 oracle 置信度保持 `medium`，不假装是 `high`。
- **备选**：① 只在文档里写清幅度、不做机器校验（放弃：文档与实现仍会漂移，漂了也没人知道）② 把规则表做成 YAML/JSON 配置（放弃：规则里含判据逻辑（归一化、矩形并集、角色集合），配置化会把逻辑挪到更难读的地方；要外部化的是**幅度**，判据逻辑留在代码里更好测）③ 只补新规则、不动幅度来源（放弃：M1 卡在 91.8% 的根因就是自证判据，不动它这条指标永远上不去）④ 把新规则的阈值交给「大家投票」（放弃：拍出来的阈值没有实测背书，改版式就会误判）。
- **后果**：质量引擎的规则从 8 条变 11 条，**零缺陷夹具必须真的长得像一页 PPT**（有卡片、每页结论互不相同、版心占用率够高）—— 否则基线本身是脏的，后面所有扣分断言都不可信；`spec/verify/helpers.ts` 的 `makeCleanSlide` 因此改为按真实版式的几何构造。判据外部化率从 91.8% 升到 100%（M1 达标）。代价：改一次扣分幅度要同时改文档与表（但这正是「幅度是有依据的」的意思）；新规则会让一部分现有文稿掉分 —— 这是把此前看不见的缺陷显出来，不是误报。

### ADR-016 · 字体 fallback 链：SVG 侧是 CSS 栈，PPTX 侧是单名

- **背景**：`docs/backend-features.md §J EXP-06` 要求「字体名 fallback 链保证中英混排」，但**从未给出链的内容** —— 这条要求在 spec 里长期挂着一个未决歧义（AMB-003）。实现侧是各写各的：SVG 渲染器直接吐主题的 CSS 字体栈（`'Manrope, system-ui, sans-serif'`），**里面没有一个覆盖中文的字体族**；真落到 `system-ui` 时用的是操作系统挑的中文字体 —— 同一份 SVG 在两台机器上字形不同。PPTX 侧则写死一个 `'Arial'`（一个**不覆盖中文**的字体名），导出后在 Office 里中文全走字体替换。两边的写法都没有说明为什么。
  问题的性质要说清楚：这不是「渲染错了」而是「**产物不确定**」—— 预览与导出不一致只是表象，根因是「谁来挑中文字体」这件事被甩给了操作系统。
- **决策**：
  1. **两条链的形状由目标格式决定，不由我们选**。SVG 是浏览器里的 CSS 字体栈，**可以**有多项；PPTX 的 DrawingML 分列 `<a:latin>`（拉丁）/ `<a:ea>`（东亚）/ `<a:cs>`（复杂文种）三种字形，**没有「链」这个概念** —— `pptxgenjs` 的 `fontFace` 会把同一个名字写进三处。所以 PPTX 侧只能**单名**。
  2. **SVG 侧的链序是：主题拉丁字体 → 显式命名的 CJK 族 → generic 兜底**。四个 CJK 族按「最可能装得上」排序：`'Microsoft YaHei'` → `'PingFang SC'` → `'Noto Sans CJK SC'` → `'Source Han Sans SC'`。**CJK 族必须排在第一个 generic 族之前** —— 排在后面等于没写：`system-ui` 在多数系统上确实能显示中文，但那是「操作系统挑的」，换台机器就不一样。
  3. **PPTX 侧取 `'Microsoft YaHei'`**：它在 PPTX 的主战场（Windows/Office）上最通用，且**覆盖拉丁字母** —— 一个名字覆盖中英混排，正是单名方案下唯一正确的选法。
  4. **链的单一真相源是 `packages/core/src/engine/typography.ts`**（`withCjkFallback` / `CJK_FALLBACK_FAMILIES` / `PPTX_FONT_NAME`），SVG 渲染与 PPTX 导出共用。`withCjkFallback` 是**幂等**的：主题自己已经写了 CJK 族就原样返回。
- **备选**：① 什么都不做，继续依赖 `system-ui`（放弃：产物不确定，跨机器字形不一致，且这正是 EXP-06 要解决的事）② SVG 与 PPTX 都用单一 CJK 字体名（放弃：SVG 侧牺牲了拉丁字形的品牌感 —— 主题字体本来是有设计意图的）③ PPTX 侧按 run 逐个指定中英两种字体（放弃：IR 里只有 `style.fontFamily` 一个字段，要混排就得改 IR 结构 —— 那是波 2 版式契约的事，不在一条渲染决策里顺手改掉）④ 把 CJK 族排在 generic 之后（放弃：等于没写）。
- **后果**：SVG 的 `<style>` 块与 PPTX 的文本运行从此**显式**覆盖中英混排，且这个事实有判据可查（SPEC-EXP-006 的两条判据，验的是产物里真正写出来的字体声明，不是函数返回值）。代价：SVG 里多了一长串字体名；主题若自带 CJK 族，`withCjkFallback` 不插手（幂等），所以自定义主题不会被打乱。

### ADR-017 · 卡片碰撞的 10px 是安全距，不是容差

- **背景**：`docs/backend-features.md §I QLT-03` 只写了「卡片/层 AABB 碰撞检测（10px 缓冲）」，**「缓冲」一词两读**：(a) 容差 —— 重叠不超过 10px 不算碰撞；(b) 安全距 —— 两块间距不足 10px 即算碰撞。两者在「重叠 0~10px」与「间隙 0~10px」两条带上结论相反，而这两条带恰恰是这条规则**存在的理由**。
  实现侧当时取的是容差读法：重叠 ≤ 10px 放过，间隙一律放过。后果是两张只隔 5px 的卡片被判为「没碰撞」—— 而 5px 间距在带描边、带阴影的卡片视觉语言里就是**糊成一块**，正是这条规则要抓的缺陷。
- **决策**：
  1. **10px 是安全距**：两块之间必须留出 10px 才算「分开的」，否则判碰撞。**恰好 10px 判不碰撞**。
  2. **间距用单个标量度量**：`separation(a, b) = max(dx, dy)`，其中 `dx = max(b.x − (a.x+a.width), a.x − (b.x+b.width))`，`dy` 同理。**负值表示重叠、0 表示相接、正值表示间隙** —— 一个数覆盖三种关系，不必为「相接」单开分支，判据也就没有「重叠容差」与「间隙阈值」两套需要对齐的参量。
  3. **只查 `role ∈ {card, layer}`**：标题、图标、连接线与卡片重叠是版式的常规手法，不参与。
- **备选**：① 维持容差读法（放弃：抓不住「挤在一起」，而这是自动排版最常见的失误）② 两条带都判碰撞（重叠 0~10px 判、间隙 0~10px 也判）—— 本决策已经是这个形态 ③ 两条带都不判（放弃：等于取消这条规则）④ 把 10px 做成可配置阈值（放弃：QLT-10「规则可配置化」是 S4 的需求，现在做会让判据失去固定值；阈值表化的路子已经在 ADR-015 里铺好了）。
- **后果**：真实版式的输出不受影响 —— 实测 8 种版式 × 8 套主题，最小间距是 20px 且零重叠，**零误报**。改动的是**缺陷识别能力**：间距 5px 的两张卡现在会被抓出来（此前放过）。判据侧同步补齐了分水岭用例（重叠 5px → 判碰撞；间隙 5px → 判碰撞；间隙恰好 10px → 判不碰撞），把裁决固化进验收。

### ADR-018 · 语义住在字段里，不住在 ID 里

- **背景**：波 0 的 ADR-014 修掉了「一键修复洗掉语义前缀」这个缺陷，但采用的是**止血**手法 —— 保留 ID 前缀。语义因此仍然住在字符串里，而全仓有**三处消费方在猜 ID**：
  1. `svgRenderer` 用 `el.id.startsWith('header_')` 决定元素走模板层还是内容层；
  2. 前端主题重映射用 `el.id.startsWith('header_')` / `el.id.includes('accent')` 决定配色；
  3. 质量引擎的 ID 重排用 `semanticPrefix(id, …)` 从 ID 里抠语义前缀。

  「字符串即语义」意味着**任何一次重命名都是事故** —— 换模板时改个前缀、把 ID 规范化一下、给元素换个 ID，元素就掉出模板层、不再跟随 accent 色。这类事故没有编译期提示、没有类型提示，判据也测不出来（测试同样在猜 ID）。

  顺带在同一条链上查出一处**真 bug**：主题重映射有三份抄写（App 的主题快切、Workbench 的换模板、TemplateCenter 的应用模板），其中 App 那份给 divider 写的是 `style.color`，而分隔线画的是 `style.backgroundColor` —— **换主题后强调线不换色**。三份实现、三种行为。
- **决策**：
  1. **语义住进显式字段**：`SlideElement.variant`（顶层、带类型）。ADR-012 当年写的是 `metadata.variant`，本次**不照抄** —— `metadata` 是给 AI 补丁用的无类型自由字段，语义契约放进那里就失去类型检查，判据也无法机械校验「取值合法」。顶层字段能被 TypeScript 与验收用例同时把关。
  2. **变体的全部语义收进一张表**（`packages/core/src/engine/elementVariant.ts` 的 `ELEMENT_VARIANTS`）：层归属（background / template / content）、是否跟随 accent 色、ID 语义前缀。表少一行 = 一处「这里该怎么办」的隐式约定 —— 那正是本 ADR 要消灭的东西。渲染层、主题重映射、ID 修复一律**读表**。
  3. **`role` 与 `variant` 正交**：`role` 回答「这是什么东西」（标题 / 卡片 / 徽标），`variant` 回答「**它是哪个版式槽位**」（页眉 / 页码 / 时间轴节点 / 架构层盒）。一个 `role: 'card'` 可能是 `grid_card` 也可能是 `kpi_card`，而这个区别正是配色与分层要的。
  4. **唯一兼容层**：`legacyVariantOf()` 是全仓唯一一处解析 ID 语义的地方，且**只在 `variant` 字段缺失时**触发（按 ID 前缀猜，猜不到按 role 兜底）。读入旧 IR 时用 `withVariants()` **幂等**补齐（服务端 `listSlides` / `requireSlide` / `importProject`，前端 `getSlide`）—— 兼容层是一次性迁移的入口，不是语义依赖。
  5. **ID 退化为派生结果**：`{variant 的 idPrefix}_{slideId}_{序号}`。ID 重排不再从旧 ID 抠语义；元素被洗成不含语义的 ID 也不丢语义。
  6. **主题重映射合并成一份**（`packages/core/src/engine/themeRemap.ts`），顺带修掉强调线不换色的 bug。
  7. **「全仓零处解析 ID」钉成不变量**：AC-CORE-017 做源码级扫描（去掉注释后不得出现任何 `.id.` 后接字符串方法的调用）。
- **备选**：① 继续让 ID 前缀承载语义（放弃：一次重命名就是一次静默事故，且测试也在猜 ID，等于没有防线）② 用 `metadata.variant`（放弃：无类型袋，取值退化成字符串比较，判据无法机械校验合法性）③ 把语义并进 `role`（放弃：`role` 是「什么东西」，塞进「哪个槽位」会让一个 role 对应多种分层与配色，反而更糊）④ 一次性重写历史库补齐 `variant`（放弃：读入时幂等补齐即可；重写库是运维动作，换不来任何行为差异）。
- **后果**：64 组黄金快照需要重建 —— 差异只有每个元素多一个 `variant` 字段（648 行新增、0 行删除），没有几何或内容变化。主题重映射从此只有一份实现（accent 线换主题会真的换色，这是用户可见的修复）。代价：`variant` 是**可选**字段（已存的旧 IR 没有它），因此每条链路仍必须经由 `variantOf()` 读，不能直接 `el.variant`；且**旧伤治不了** —— 在 ADR-014 之前被洗成 `text_s1_1` 的 ID，其语义已经不可恢复，只能按 role 兜底。止血能防新伤，治不了旧伤。

## 13. 质量属性场景

> 架构决策由质量属性驱动。以下场景说明架构如何满足具体约束。

### QA-1 · 性能：大纲生成 P95 < 25s
- **需求**：6 页大纲 + 内容槽位生成。
- **架构响应**：① 槽位 schema 化，输出结构紧凑 ② 模型选快档 ③ Prompt 前缀缓存 ④ 上下文裁剪只传必要字段 ⑤ 生成异步化 + SSE，前端不被阻塞。
- **验证**：`model_calls` 表统计 latencyMs，按 Agent 分位数监控。

### QA-2 · 可用性：主模型完全不可用时功能不中断
- **需求**：Gemini 5xx / 超时 / 配额耗尽。
- **架构响应**：① 降级链到 secondary ② 再降级到确定性本地实现 ③ 本地实现按 topic 动态生成而非固定文案 ④ 质量闸门在降级路径同样生效 ⑤ 降级率进告警。
- **验证**：混沌测试——注入模型故障，断言端点仍返回合法内容。

### QA-3 · 安全：越权与提示注入
- **需求**：A 用户不能读 B 的项目；用户文档不能劫持系统提示。
- **架构响应**：① 每个资源查询强制带 `userId` 条件（SEC-01）② 文档内容作为数据注入并显式标注边界（DOC-06）③ AI 输出必须过 Zod 才进系统（SEC-03）④ 上传文件魔数校验 + zip bomb 防护。
- **验证**：越权测试用例覆盖每个资源端点；提示注入 case 纳入 eval 套件。

### QA-4 · 可维护：版式引擎变更不引入静默回归
- **需求**：改一个版式，不能悄悄改坏其它 7 种 × 8 套主题。
- **架构响应**：① 64 组黄金快照测试进 CI ② 版式是纯函数无隐藏状态 ③ 快照 diff 需人工审阅。
- **验证**：CI 快照门禁；PR 中快照 diff 作为评审重点。

### QA-5 · 可观测：单次生成的完整归因
- **需求**：用户报"这次生成很慢很贵"，要能定位到具体调用。
- **架构响应**：① `traceId` 贯穿 HTTP/日志/记账/任务 ② `model_calls` 记 provider/model/tokens/cost/latency/promptVersion ③ `slide_versions.patch` 记 AI 实际改了什么 ④ Prompt 版本可回放。
- **验证**：从任一 `traceId` 可完整还原该次调用的输入、输出、耗时、成本。

### QA-6 · 可扩展：项目量增长 100 倍
- **需求**：单实例不能成为瓶颈。
- **架构响应**：① API 无状态水平扩展 ② Worker 独立扩容 ③ 队列 `SKIP LOCKED` 保证不重复消费 ④ 产物入对象存储不进 DB ⑤ 列表查询强制分页 + 索引。
- **验证**：压测 100 并发 × 1000 项目；观察 P99 与队列深度。

## 14. 架构演进路线

```
现状（V0）                        目标（V1）
────────────────────────────────────────────────────────────────
单文件 Express 服务               Bun + Hono 双进程（API / Worker）
  4 个 AI 端点                      完整资源化 API（40+ 端点）
  ↓
localStorage 存项目              PostgreSQL 存项目 + 版本表
  ↓
前端独算版式与质量                @ppt/core 共享内核，前后端同源
  ↓
AI 直接产 SlideIR                 AI 产内容槽位 → 确定性编译
  ↓
全量元素覆写                      IRPatch 增量 + 质量闸门
  ↓
浏览器导出（中文 PDF 有缺陷）      服务端渲染 + 对象存储 + SSE
```

### 四次关键跃迁

| 跃迁 | 从 | 到 | 触发条件 | 风险 |
|---|---|---|---|---|
| **T1** | 前端独算 | 共享内核 | S0 完成 | 需前端 import 路径迁移，影响面可控 |
| **T2** | 本地存储 | 服务端持久化 | S1 完成 | 需双写过渡期，注意冲突处理 |
| **T3** | AI 直出 IR | 内容槽位 | S2 完成 | **影响既有 Prompt 与版式**，需快照+eval 双保险 |
| **T4** | 浏览器导出 | 服务端导出 | S3 完成 | 字体与渲染环境差异，需 CI 渲染比对 |

**T3 是风险最高的一次跃迁** —— 它同时改变 Prompt 契约、版式输入与渲染结果。因此 T3 的准入条件是：eval 套件上线 + 64 组快照就位 + 旧路径保留一个版本周期。
