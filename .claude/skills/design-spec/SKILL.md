# 设计文档 → 可执行 Spec

## 这个技能在解决什么

把设计文档**重排成 YAML** 是最容易的做法，也是最没用的做法。目标不是格式，是链路：

```
需求意图 → 行为契约 → 正确性判据 → 独立 Oracle → 可执行验证 → 执行证据
```

任何一环断了，Spec 就退化成"看起来很完整的文档"——Coding Agent 无法据此实现，验收方无法据此判定。**格式漂亮但链路断裂，比没有 Spec 更危险**，因为它会让人误以为问题已经解决。

## 四条不可让步的原则

1. **不编造业务规则**。文档没说的，不要替它决定。合理推导要显式标注为推导，未经确认的假设要显式标注为假设。
2. **不自我证明**。"实现和测试都是 Agent 写的，测试过了"不是正确性证据。关键判据必须来自被测系统之外。
3. **不可判定就承认**。写不出判定条件的条款，说明它还没被理解 —— 标 `PENDING`，不要编一个看起来合理的判据。
4. **不用降低标准换成功**。删要求、降阈值、改预期、缩覆盖来让测试变绿，是本任务最严重的失败模式。

## 阶段 A · 仓库与文档勘察

在理解现状之前，**不要**大规模创建文件或重构代码。

1. **找出源材料**：设计文档、PRD、架构说明、现有实现、数据模型、接口定义、既有测试、CI 配置。
2. **盘点可用工具**：测试框架、Schema 校验库、lint/format、CI workflow、覆盖率工具。**优先复用**——新引入一套框架的代价是它自己也成了未验证的依赖。
3. **建立初步映射**：文档条款 ↔ 现有实现 ↔ 既有测试。标出三类：
   - 已有实现且有测试 → 可作为回归基线
   - 已有实现但无测试 → **契约捕获点**，优先级最高
   - 文档有、实现无 → 真正的待建项
4. **识别不匹配**：文档说了但实现不是这样（**文档可能是错的**，这本身是重要发现，要报告而不是默默以实现为准）。

> 勘察阶段的产出是判断，不是文件。先形成判断再动手。

## 阶段 B · Spec 建模

### 拆分的最小单元

**一条 clause = 一个可以独立写出一条验收判据的原子要求。**

按这些维度切分文档：

| 维度 | 说明 |
|---|---|
| 行为边界 | 一个动作的一个明确结果（不是"系统要 X"这种整句） |
| 状态迁移 | 状态机的每一条合法边 + 非法边 |
| 不变量 | 任何时刻都必须成立的性质（如"元素 ID 全局唯一"） |
| 权限边界 | 谁能做、谁不能做、越权时的**确切**响应 |
| 失败路径 | 每个输入的拒绝分支及其错误标识 |
| 输入输出契约 | 字段、类型、必填性、边界值 |
| 非功能约束 | 性能、容量、一致性等级 |
| 显式非目标 | 明确不做的事（同样需要追溯） |

### 每条 clause 的必备字段

字段语义与完整示例见 `references/spec-model.md`。最小形态：

```yaml
id: SPEC-AUTH-001
type: business            # business | technical | quality | governance
risk: high                # high | medium | low
statement: <一句可判定的陈述>
source: { doc, section, quote }     # 必填：原始文档出处
preconditions: []
behaviors:  [ { when, then } ]
boundaries: []
failure:    []
acceptance:
  - criterion: <可机械执行的判定条件>
    oracle: { tier, source }        # 必填：判据从哪来
    verification: { kind, target, command, pass_when }
maturity: automated                   # automated | semi | manual | none
```

### 识别不确定性

给每条要求打上来源分类，**不要抹平**：

| 分类 | 处理 |
|---|---|
| **明确要求** | 文档白纸黑字写了的 |
| **合理推导** | 由明确要求逻辑推出 —— 标 `derived_from` + 推导依据 |
| **未确认假设** | 我们的猜测 —— 标 `assumption`，进歧义清单 |
| **相互冲突** | 文档内部矛盾 —— 并列保留，标 `conflict`，**不得自行裁决** |

### 暂停规则（关键）

歧义分两类，处理方式不同：

- **影响正确性或安全性的关键歧义** → 记录为 `AMB-NNN`，**暂停受影响条款的定稿**（可以写，但必须标 `status: blocked`），**其余条款继续推进**。
  - 判据：改动它会不会导致做错事？不会 → 不阻塞。继续。
- **不影响正确性的表述歧义** → 直接采用最合理解读，记录决定即可，不阻塞。

**绝不允许**：为了让流程继续而替用户猜一个业务规则，然后把猜测写成看起来很确定的条款。

## 阶段 C · 验证器与基准建立

### Oracle 分级 —— 本技能的核心

每条验收判据都要回答：**这个"正确答案"是从哪来的？**

| tier | 来源 | 可信度 |
|---|---|---|
| `authoritative` | 权威业务规则原文（法规、需求文档明确条款） | 最高 |
| `expert` | 专家/领域负责人确认的基准案例 | 高 |
| `formal` | 类型、schema、不变量等形式化约束 | 高（但只覆盖它能覆盖的部分） |
| `statistical` | 统计评估、分布性判据 | 中 |
| `human` | 人工评审、人工盲评 | 中（需记录评审者与判据） |
| `self-derived` | **从被测实现反推出来的** | ⚠️ **不可作为关键判据的唯一依据** |

> `self-derived` 不是不能写，但必须显式标注，且**关键条款不能只有它**。一条判据如果只是"实现返回什么，测试就断言什么"，它不验证任何东西 —— 它只防止回归。

### 验证器类型选择

| 需求性质 | 用什么验证器 |
|---|---|
| 明确的输入 → 明确输出 | 单元/契约测试，精确断言 |
| 适合属性描述的（不变量、往返、单调性） | 属性测试（定义输入空间 + 性质 + 边界） |
| 精确预期难获得但有可比对象 | 差分测试（新旧实现 / 参考实现对比） |
| 关系型正确性（等价类、顺序不变量） | 蜕变测试（metamorphic） |
| 历史缺陷 | 缺陷回放测试 |
| 主观质量（文案好坏、设计好坏） | 人工盲评（记录评审者、量表、样本） |

> **不要把 LLM Judge 当作所有类型问题的通用 Oracle**。它可以是辅助信号，但要有：明确评分量表、固定样本集、多个评审者的一致性检查、与人评的定期校准。当主 Oracle。

### 关键要求要有"检出代表性错误"的能力

**光有测试不算数，测试要能抓错。**

对每条**关键**判据，问："如果实现写错了，这套验证器会失败吗？" 如果答案是"不一定"，就补一个能抓错的用例，或用差分/属性测试扩大检出面。

### 复用优先

- 仓库已有测试框架 → 用它
- 已有 schema 校验 → 用它
- 已有 lint / typecheck → 把它们纳入验证入口
- 不要为了统一格式引入新框架 —— 每个新依赖都是新的未验证假设

## 阶段 D · 执行与缺口分析

1. **先验证 Spec 和验证器，再跑实现的测试。** 顺序反了会分不清是实现的锅还是验证器的锅。
2. **执行现有实现的测试**，记录真实结果、失败原因、未验证项。
3. **注入代表性错误**（mutation check）：故意把实现改错，看验证器是否报错。
   - 验证器抓不到注入的错误 → 验证器本身不合格，补强
   - 这一步经常是整个任务信息量最大的环节
4. **若任务明确要求改实现**：仅当需求与验收判据已足够明确时才动手；否则**先交付 Spec 与验证基础设施**，把阻塞问题单独列出。
5. **未执行的验证不得描述为已通过。**

### 结论三态，禁用二值

| 结论 | 含义 |
|---|---|
| `PASS` | 验证器实际执行了，判据可信，证据完整 |
| `FAIL` | 验证器实际执行了，未满足判据 |
| `INCONCLUSIVE` | 缺必要证据 / 验证未执行 / 判据不可信 / 环境缺失 |

**缺少必要证据时不得报 PASS。** 这一条要落到字面上 —— 报告里每一个 PASS 都要能指出是哪条判据、哪个测试文件、哪次执行。

| 基准数据及来源说明 | 支撑关键 Oracle | — |
| 追溯映射 | 文档条款 → Spec ID → 验证器/测试 → 证据 | `templates/traceability.md` |
| 验证报告 | PASS / FAIL / INCONCLUSIVE / 未覆盖 / 未解决 | `templates/traceability.md` |

**文件格式、目录结构、工具选型基于仓库现状决定。** 不要为了追求统一格式引入不必要的框架。

## 完成标准

只有同时满足以下条件，才可以声称完成：

- [ ] 原始文档的关键要求**均有追溯关系**，遗漏项有明确说明
- [ ] 关键要求具有明确、可判定的验收条件
- [ ] 关键 Oracle 来源可信，**不依赖被测实现自我证明**
- [ ] Spec 可通过机器校验，关键验证项**可实际执行**
- [ ] 关键异常路径和代表性错误有对应测试（且验证器确认能抓错）
- [ ] 测试结果与证据可复核、可复现（能指出判据、测试、执行环境）
- [ ] 未解决的歧义、未验证要求、已知限制**被明确披露**
- [ ] **没有通过降低验收标准来制造成功**

## 关键实践

### 先做一个经过验证的最小闭环

不要一次性建立庞大、空洞的 Spec 体系。正确顺序：

1. 选出**风险最高的一条条款**（通常是权限边界或数据正确性）
2. 为它写 Spec → 建验证器 → 注入一个错误 → 确认验证器抓到了
3. 这个闭环跑通后，**模式**才可信，再横向扩展

一个跑通的最小闭环，胜过一百条没人验证过的条款。

### 防止标准漂移

未经授权，不得为了让测试通过而：删除要求 / 降低阈值 / 修改预期结果 / 缩小覆盖范围。

若确实需要调整，必须记录：改了什么、为什么改、谁批准的。新阈值不得低于同类型条款的既有下限 —— 单点下调会让整份 Spec 的严格性失去参照。

### 报告要说实话

最终报告简洁说明四件事：

1. **生成了什么**（哪些文件、覆盖哪些条款）
2. **覆盖了什么**（哪些有验证、哪些没有）
3. **实际验证了什么**（真的跑了什么、结果如何、证据在哪）
4. **哪些结论仍不可信**（证据不足的、假设的、被阻塞的）

最后给下一步最值得解决的一个问题 —— 而不是罗列全部待办。
